# 加深批量计划编译与延展 module：本期内部重构

Status: implemented（内部重构；验收边界见 implementation.md）

日期：2026-10-12。用户最新决定：优先完成原架构报告③的优化，本期只做行为保真的内部重构。一张闭环工单已实施，源码提交 `1f3f70b`，本轮验收见 [implementation.md](implementation.md)。

依据：[当前阶段决策](grill.md)、原架构报告候选③及 ADR-0026。ADR-0027 的完整协议/审批升级目标保留为后续阶段，见 [upgrade-spec.md](upgrade-spec.md)，不作为本票必须交付的契约变化。

## Problem Statement

自动提交和计划卡确认分别掌握计划解析、引用延期、快照对齐、已覆盖步骤分类及追加时的序号映射。已有辅助函数返回多份平行序列，调用方必须正确配对后才能落可执行事实。新增或维护规则时需要同时改两条路径，重构只换六元组类型不能降低调用知识。

本期目标是集中这些既有规则，并保留当前 Tool、提案、Run、Worker 和前端行为。外部协议迁移、严格版本批准及重新预览会带来额外兼容成本，不与本期重构绑定。

## Solution

围绕计划形成可执行事实的阶段加深现有计划 module：复用动作 adapter/schema，内部封装参数解析、延期引用、快照、步骤分类、对应关系及追加/原位修订落库。自动提交与确认入口只保留真实的事务、授权分流、回执和生命周期接线，不再拆装编译中间序列。

保持现有扁平请求及持久数据格式、九项动作和结果投影；无需新 HTTP/Tool、新计划语法、版本迁移或前端工作流。Run Worker 继续管理推进、等待、取消和恢复，受控业务执行继续复用已落地的 Operation module。

## User Stories

1. 作为维护者，我希望两条入口共用计划编译与落库规则，以便规则只需维护一次。
2. 作为维护者，我希望调用方无需配对载荷、快照、解析与序号集合，以便难以误用 interface。
3. 作为维护者，我希望内部直接复用动作参数 schema 和现有 adapter，以便不复制业务规则。
4. 作为用户，我希望现有工具参数和回执保持可用，以便架构优化不要求重新表达任务。
5. 作为用户，我希望现有计划卡、任务进度和操作历史保持可用，以便无需学习新界面。
6. 作为用户，我希望当前三档分流与阈值保持，以便重构不静默改变已上线行为。
7. 作为用户，我希望相同已有步骤继续复用，以便不重做已完成项。
8. 作为用户，我希望待执行参数修订保留身份、成功后的变更保留历史，以便任务可核对。
9. 作为用户，我希望前步输出引用及追加批次映射继续正确，以便多资料任务可运行。
10. 作为用户，我希望已有快照及执行端重验保持，以便不会覆盖后续手动修改。
11. 作为用户，我希望取消和执行身份门禁保持，以便中止后不出现额外写入。
12. 作为用户，我希望主事务失败不留下半份计划或伪成功回执，以便失败可安全恢复。
13. 作为用户，我希望独立失败诊断继续保留，以便错误不会被重构吞掉。
14. 作为用户，我希望等待后台任务及部分失败保持原结局，以便成功工作不丢失。
15. 作为用户，我希望重启恢复保留原 Run/Operation/Job 身份与成功结果，以便不会重复执行。
16. 作为用户，我希望已有提案和回执继续读取和确认，以便不因内部类型变更使历史卡失效。
17. 作为维护者，我希望通过现有公开入口验收行为，以便测试不依赖内部文件或 helper 布局。
18. 作为维护者，我希望已核实的行为差异单独登记，以便不把纯重构误报为授权修复。

## Implementation Decisions

### Module 与 seam

- seam 放在计划形成可执行事实的阶段；在现有计划域内收拢 implementation，无须预先规定新目录、类或策略层。
- 内部直接复用现有参数解析、引用绑定、快照及动作登记能力，移除自动提交与确认两路的重复编排知识。
- public interface 接收入口已有计划、上下文及事务，隐藏子批分类、快照对齐、已覆盖/替换映射与序号转换，返回入口真正需要的 Run/变更结果或错误。
- 内部可使用一个清楚的具名编译结果，但该类型不能把原六份对应序列原样暴露给两条入口。验收同时检查重复知识被删除，不能只看新增包装函数。
- 动作解析复用现有 OperationSpec 和 schema；当前动作面不扩大，可消除同值映射等冗余维护点，不搭 schema 生成框架或新增批量能力 catalog。

### 保持行为与数据兼容

| 范围 | 本期约束 |
| --- | --- |
| 请求/提案/Run格式 | 保留现有 Tool、扁平字段并集、持久 JSON、类型名及结果投影；不新增格式版本或强制旧卡重新预览 |
| 参数与引用 | 保留既有普通参数、null/省略/字段投影解释、延期校验和绑定后完整校验；不新增错误原因或改变输入接受范围 |
| 步骤分类 | 同目标同参数覆盖复用，待执行修订保身份，成功后变更追加；失败/跳过及创建类去重沿用现有语义 |
| 延展与批准 | 保留现有目标选择、版本递增、旧卡确认及档位分流；本期不引入确定新建/延展意图、基础版本 CAS 或新恢复流程 |
| 等待/取消/恢复 | 保留现有状态机、领域 Job 等待、部分失败、原身份重试及启动对账 |
| 前端/模型可见面 | 不更换工具声明、Prompt、确认/拒绝动作、计划卡布局或消息事件 |

- 当前未确认 AUTO_APPROVE Run 的阈值内自动延展、旧卡合入活跃 Run/终态后另建 Run、无关联合字段投影和 null 解释均作为事实基线登记，不将其宣称为 ADR-0026 的期望规则。
- 当前实现保真不表示上述差异已经闭合；授权修正和审批规则升级是后续独立行为变更，不借本票静默修复或放宽。
- 已有 model_construct 等部分载荷实现可封装在内部；保持当前使用前提及最终验证，不因抽象扩大其适用范围，也不为去掉一个调用而改造整套业务载荷。
- 本期不完全消除外部字段并集，新增动作仍有外部 schema 维护负担；这是保留协议的明确取舍，不能声称完整协议升级已经完成。

### 事务与执行边界

- 入口拥有 AsyncSession 的 begin/commit/rollback；共享计划 implementation 在传入事务内读取/写入/flush，不自行提交或另开事务框架。
- 主事务中的 Run/Operation/计划投影、触发 Job、ChatTurn 绑定及 Proposal/Effect 成功结果维持原子性；入口的不同控制绑定语义保留。
- 保留 Effect 前置准备与成功回执重放顺序，回放不重扣提交额度；工具预算及独立提交预算保持原计数口径。
- 保留提交处持久取消/执行身份门禁、Worker 每步最终授权/快照检查、主事务回滚后的独立失败记账及其并发保护。
- Worker 不消费编译中间序列，不承担计划载荷修补；领域动作仍只由受控执行入口实际执行。

## Testing Decisions

- 使用已确认的现有 seams：计划公共提交、Proposal 确认、Run 查询/Worker 推进；通过真实 SQLite 的 Run/Operation/Proposal/Effect/Job 结局验收，不测私有 helper 的文件布局。
- 优先复用 `test_agent_batch_run.py`、`test_agent_run_waiting.py`、`test_agent_multi_source_run.py`、`test_chat_turns_recovery.py`，覆盖两路、三档及累计阈值、快照、步骤分类/映射、WAITING_JOB、取消、部分失败和恢复不重做成功项。
- 对已核实的 AUTO_APPROVE 例外及旧卡合并行为保留现有断言作为保真证据；授权修复另列行为规格，不能在本票改断言后称为零行为变化。
- 外部格式不改，前端现有计划卡用例及 OpenAPI/TS契约检查用于证明消费方兼容，无需新增 UI 流程、通用测试体系或协议迁移黄金集。
- 行为保持时不为新内部类型单独补镜像测试；既有覆盖不足且本次确实触及关键保证时，只增加必要的公开入口验证。
- 验收记录区分自动化、模型/网络替身、真实 SQLite/Worker、真实模型与真实 Tauri；未运行的模型/真机项明确列出，不把旧测试数量当本轮验收。
- 仅跑本次相关现有测试和触及类型/规范/契约门禁；历史失败另留基线证据，不借机扩大修复范围。

## Out of Scope

- 新 action+params 对外格式、显式新建/延展协议、格式版本及历史迁移、严格 null/无关字段新规则。
- 新基础版本批准/CAS、改变旧卡确认或目标选择、修正 AUTO_APPROVE 例外、步骤依赖编辑策略变化。
- 新重新预览 API/Tool/前端按钮、预览来源关联及跨请求语义去重；这些属于后续协议/审批升级。
- 新动作、通用 DAG、任意值引用、批量注册框架、供应商 schema 适配框架、第二套任务系统。
- UI 重设计、新增配置、业务数据库迁移、编码规范修改和历史测试覆盖率补齐。
