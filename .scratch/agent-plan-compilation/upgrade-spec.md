## Problem Statement

用户通过 Agent 批量整理资料、建课、导入来源和生成学习计划草案时，自动提交与计划卡确认两路需要分别处理参数校验、引用延期、快照、已有步骤分类和依赖映射。相同业务规则分散在调用方，维护者接入新动作时还要同步动作名单、多动作字段并集和工具声明，容易遗漏校验与授权边界。

当前自动批准档存在运行中直接追加目标或改变参数的例外；旧计划卡确认会自动合入当前活跃 Run 并提升版本，目标任务结束后甚至会新建 Run。这些行为不能准确表达用户批准的确定任务、参数和计划版本。

直接替换输入格式又会影响旧待确认卡、在途任务与回执。用户需要新旧数据都可核对、已完成项不重做、失效批准不能直接执行，并且能通过页面或 Agent 完成重新预览。

## Solution

将计划编译与延展加深为一个 module：接收明确的新建或延展意图、动作专属类型化参数及入口执行上下文，内部完成校验、快照、已有步骤分类、引用映射和可执行事实写入。自动提交与计划卡确认复用同一 implementation，不再拆装多份对应序列；入口只处理自身授权分流、事务、回执和生命周期接线。

沿用 Run、Operation、Proposal、ProcessingJob 与 ChatTurn 的现有事实角色。Plan Card 负责批次批准，Run 管任务执行，Operation 管受控写入事实，Worker 管推进、等待、取消和恢复；LangGraph checkpoint 与 SSE 不能替代这些持久事实。

新计划项按动作区分参数，复用现有 OperationSpec；动作显式启用批量能力，默认关闭。运行中新增目标或修改参数均重新出计划卡；延展批准绑定确定的 Run 与基础计划版本，在提交事务内校验。旧回执保留、旧在途任务继续恢复，旧待确认卡须重新预览后再确认。

用户仍使用现有对话、计划卡、任务进度和操作历史。前端补齐格式兼容、批准失效提示与确定性重新预览动作，不增加步骤编辑器或重做视觉布局。

Depth 的验收是两条入口所需知识减少：动作校验、快照对齐、覆盖/替换/追加分类及序号映射只在计划 implementation 内维护。具名类型可以用于内部表达，但仅把六元组换成具名类型不算完成。

## User Stories

1. 作为用户，我希望 Agent 一次提交资料整理或多步任务，以便不必逐项进入页面操作。
2. 作为用户，我希望看到计划的逐项动作、目标、参数和依赖，以便知道批准范围。
3. 作为用户，我希望新建任务与延展已有任务明确区分，以便不会把新意图并入另一项工作。
4. 作为用户，我希望 Agent 在任务归属有歧义时先追问，以便任务不会被隐式替换。
5. 作为用户，我希望请求批准档始终先给计划卡，以便未经确认不创建执行任务。
6. 作为用户，我希望帮我批准档的新任务继续遵循既有动作级别和累计阈值，以便本次改动不静默放宽权限。
7. 作为用户，我希望完全访问档仍自动提交允许的新任务，以便既有自动执行能力保留。
8. 作为用户，我希望活跃任务增加目标或改变参数时在任何档位重新确认，以便批准不会被扩张。
9. 作为用户，我希望提交相同目标及相同参数时复用已有步骤，以便不会重复操作同一对象。
10. 作为用户，我希望创建类步骤不会仅因同名或内容相似被合并，以便不同创建意图保留。
11. 作为用户，我希望错误动作、缺失参数和多余字段得到可解释的错误，以便 Agent 能追问或修正。
12. 作为用户，我希望显式 null 不被当作清空指令或静默忽略，以便提交内容与执行含义一致。
13. 作为用户，我希望动作原有必填字段、枚举、范围和业务校验继续生效，以便类型化改造不削弱约束。
14. 作为用户，我希望计划保持现有单批规模限制且超限明确拒绝，以便不会只执行静默截断后的部分请求。
15. 作为用户，我希望建课或建目标的输出能供后续步骤引用，以便多步任务无需提前提供不存在的 ID。
16. 作为用户，我希望引用只能指向本次提交中更早的合法步骤，以便计划不会形成无效依赖。
17. 作为用户，我希望错误输出字段和不支持的引用位置在提交时被拒绝，以便错误不会留到任务执行一半才发现。
18. 作为用户，我希望来源步骤未成功或结果值不合法时后续依赖项如实阻塞或跳过，以便不会使用伪造 ID。
19. 作为用户，我希望引用绑定后仍完整校验动作参数，以便延期校验不绕过领域约束。
20. 作为用户，我希望确认卡读取既有目标的真实快照，以便批准前能核对对象。
21. 作为用户，我希望目标在预览后被修改时旧批准失效，以便 Agent 不覆盖我的后续改动。
22. 作为用户，我希望计划卡绑定确定任务和基础版本，以便确认的计划正是将要落库的变更。
23. 作为用户，我希望同一基础版本的两张延展卡不能先后偷偷合并，以便第二张必须基于新版本重新预览。
24. 作为用户，我希望重复确认同一卡只产生一次执行事实，以便重复点击或请求重试不会重复执行。
25. 作为用户，我希望任务已经结束或取消后旧延展卡不能另建任务，以便历史批准不会启动新的工作。
26. 作为用户，我希望普通执行进度变化不会使延展卡失效，以便只因参数和计划结构变化才重新批准。
27. 作为用户，我希望待执行项改参数后保留执行身份与位置，以便依赖和重试可继续核对。
28. 作为用户，我希望已成功项改参数后经确认追加新操作，以便已执行历史不会被覆盖。
29. 作为用户，我希望删除步骤、重排或修改既有依赖的请求被明确拒绝，以便不支持的编辑不会被忽略。
30. 作为用户，我希望某项失败不回滚成功项和独立后续项，以便部分工作可保留。
31. 作为用户，我希望已有失败项重试继续使用既有重试入口，以便原尝试历史和执行身份保留。
32. 作为用户，我希望等待后台任务时新增计划仍先确认且不伪造等待完成，以便依赖真实完成后才推进。
33. 作为用户，我希望取消与计划确认发生交错时遵循最终提交结果，以便取消后不新增未批准执行。
34. 作为用户，我希望任务和相关回执原子提交，以便不会看到没有执行事实的成功回执。
35. 作为用户，我希望应用失败后原任务与计划不被部分改写，并保留失败诊断，以便能够安全恢复。
36. 作为用户，我希望中断后同一逻辑提交返回原回执，以便不会重复建任务、扣提交预算或投递触发任务。
37. 作为用户，我希望新版仍能查询旧回执，以便历史不因格式升级丢失。
38. 作为用户，我希望旧在途任务重启后保留身份、参数、等待关系与已完成结果，以便不用重新批准已经获准的原计划。
39. 作为用户，我希望旧待确认卡可以查看但不能直接执行，以便新授权信息不会被替我补出。
40. 作为用户，我希望重新预览保留原请求参数并读取新快照，以便能够比较发生了什么变化。
41. 作为用户，我希望重新预览后先看到新卡再批准，以便刷新不会自动执行任务。
42. 作为用户，我希望页面和 Agent 都能重新预览计划，以便恢复能力不依赖手动页面操作。
43. 作为用户，我希望重复或并发重新预览能核对到同一有效新卡，以便不会产生多份重复批准。
44. 作为用户，我希望计划失效、重新预览中和失败状态保留参数及明确恢复动作，以便不会陷入只能重问模型的死路。
45. 作为用户，我希望新旧卡、任务进度、继续、重试、取消和历史在多主题及键盘操作下可用，以便契约改造不损伤桌面体验。
46. 作为维护者，我希望批量动作面与工具参数声明来自同一显式登记，以便新增动作无需同步字段并集与平行白名单。
47. 作为维护者，我希望计划 module 对外隐藏快照和序号对应关系，以便两条入口无需重建同一算法。
48. 作为维护者，我希望动作参数和结果复用现有 schema 与领域 Service，以便不复制业务约束或新建写通道。
49. 作为维护者，我希望格式版本、业务计划版本和执行身份分别表达，以便历史兼容不会被误当授权。
50. 作为维护者，我希望通过公开入口验证持久结果与并发结局，以便重构不绑定私有函数布局。

## Implementation Decisions

### 1. Module 职责与 interface（Q1、Q9）

- 计划 module 属于 Agent 批量任务执行域，负责输入归一化、动作参数校验、引用分析、快照策略、既有步骤分类、局部/全局序号转换，以及 Run/Operation 可执行事实写入。
- 公共 interface 提供提交计划、应用已批准计划和重新预览计划三种用途；它们共用编译与延展 implementation，不要求共用相同授权、事务或生命周期入口。
- 输入包含类型化请求、确定的新建/延展意图、入口传入的 AsyncSession 及必要授权/溯源上下文；输出为受理结果、计划卡、实际 Run 结果或结构化错误，不返回六份需要调用方相互对齐的序列。
- 入口保留事务开始/结束、预算准入、Effect 回执接线、提案状态、ChatTurn 绑定及通知；计划 module 在传入事务内写入/flush，不自行 begin、commit 或 rollback。绑定需要的执行结果通过明确对象返回，仍在入口主事务内完成。
- 受控执行继续复用现有 Operation execution 与领域动作 adapter；Worker 不承担修补计划载荷，也不被计划 module 吞并。没有必要为各项编译动作建立公开策略类、插件或独立框架。

### 2. 新计划输入与版本契约（Q2、Q5、Q8）

| 信息 | 契约 |
| --- | --- |
| 新建/延展意图 | 新建表示创建独立 Run；延展必须明确目标 Run，不能靠会话内最新活跃 Run 推断 |
| 计划项 | action 判别动作，params 只携带该动作参数，depends_on 表达本次提交中的前序步骤索引；既有目标由动作参数/定位器确定，不再借用资料整理专属 item_id 作为通用目标语义 |
| 格式标记 | 新持久提案显式标识新格式；格式版本仅服务解码，不能代替计划版本或批准 |
| 基础版本 | 延展预览由服务器读取并固化，确认时作为条件写依据；模型提供的版本或页面缓存不是授权依据 |
| 生效版本 | 新建从现有初始版本开始；实际计划变更成功提交后单调递增，进度更新、纯覆盖复用和失败回滚不递增 |
| 入口注入信息 | auth_mode、instruction_text、消息/轮次溯源及批准依据由可信执行入口提供，模型不能自行填写或放宽 |

- 新工具输入不继续接收旧扁平字段并集作为长期并行写协议。旧持久资料的兼容读取与新请求校验分开；旧字段不靠猜测重新解释为新契约。
- action 及 params 均严格校验，多余字段、动作无关字段和显式 null 返回结构化参数错误。字段省略仍按原动作必填规则和默认值处理；内部默认空值不等于用户显式 null，不得把省略字段自动序列化成被禁止的新输入。
- 单次提交沿用 1～50 项限制及前序依赖规则，超限整体拒绝，不截断。相同动作对同一既有目标在同批出现两次仍拒绝；创建类步骤没有既有目标，不套用该去重规则。
- Tool 的严格声明与服务端结构化错误均需覆盖；工具框架已拒绝的参数错误也继续遵守既有预算准入机制，不能因迁移参数校验位置改变计数。

### 3. 批量动作登记与 schema 复用（Q2、Q7、Q10）

仅以下当前动作显式启用批量；其他已注册单步动作默认不开放。

| 动作 | 既有能力 |
| --- | --- |
| update_library_item | 资料改名/归类 |
| archive_library_item | 资料归档 |
| create_course | 创建课程 |
| ingest_library_item | 导入网页资料 |
| ingest_local_document | 导入本地文档 |
| add_text_record_to_course | 保存课程文本记录 |
| add_shared_ref | 添加共享资料引用 |
| create_goal | 创建学习目标 |
| generate_plan_draft | 生成学习计划草案 |

- OperationSpec 是动作参数/结果及执行能力来源；增加最小的可选批量声明，明确是否启用及允许引用的参数位置，默认不启用。批量动作集合和 Tool schema 从该声明获得，不再手工同步字段并集、枚举和同值映射表。
- 参数 schema 派生或组合时保留原字段约束及可执行的业务校验；不得通过复制字段而丢掉 field/model validators。提交期引用校验不适用的部分采用明确延期表示，绑定真实值后必须调用原动作 payload schema 完整验证。
- result schema 提供可引用输出路径依据，动作定位器/快照读取器继续复用。计划结构字段与业务字段分离，不增加万能 action+任意 JSON 的免校验入口。
- 供应商不支持某种工具 schema 时，适配限制在工具 schema 的表达；内部类型与执行校验不能退化。沿用已支持的模型接入范围，不增加模型选择或插件能力。

### 4. 输出引用与校验时机（Q7）

- 沿用 StepOutputRef 的步骤序号与字段路径语义。新请求中的引用只能指向本次提交更早步骤；不提供任意既有 Operation ID 引用、环、分支或并行 DAG 语法。
- 消费位置仅限现有 course_id/goal_id，且必须是对应动作批量声明允许的位置；来源结果路径须在来源动作 result schema 中可确定地指向字符串值。运行时仍要求非空字符串，并由消费动作检验 UUID 等真实字段约束。
- 编译时检验引用形状、来源索引、路径、接收位置与可确定类型；自动将引用来源并入 depends_on，显式依赖去重且仅允许更早步骤。
- 普通字段的缺失、枚举、长度、范围及与引用无关的业务错误在提交时拒绝。确实需要真实输出值才能判断的条件才延期，不沿用“出现引用就放行全部 model 级错误”的宽泛判断。
- 待绑定参数不是完整业务 payload，不能以 model_construct 伪装已校验输入传给依赖完整参数的业务入口。只需既有目标信息的快照/定位能力通过明确的部分输入或既有 adapter 访问。
- 来源结果由持久 Operation 读取，不使用模型转述、SSE 或 checkpoint 中的临时值。绑定后再次完整校验，按既有 Worker 的依赖失败/单项错误/等待语义收口，不伪造成功。
- 输出值绑定属于执行状态变化，不改变已经批准的引用表达、计划版本或对象集合；解析过程中不能借机扩大目标范围。

### 5. 预览、授权与受理分流（Q3、Q5）

| 场景 | 结局 |
| --- | --- |
| 新建＋REQUEST_APPROVAL | 创建待确认计划卡，不创建执行 Run/Operation |
| 新建＋AUTO_APPROVE | 继续按现有动作级别、会话累计操作数和 10 项阈值分流；超阈值或动作不允许自动执行则出卡 |
| 新建＋FULL_ACCESS | 允许的能力自动受理；长期记忆、内容采纳、外发等既有独立边界不改变 |
| 延展＋新增目标或参数变更 | 任何档位均出计划卡，不保留未确认 Run 的 AUTO_APPROVE 直接追加例外 |
| 延展＋仅相同覆盖项 | 不新增或改写执行事实、不提升计划版本；沿用档位的提案呈现规则或返回零变更结果，不能重复执行 |
| 延展＋WAITING_USER/WAITING_JOB | 变更先确认；确认是明确动作，但不把未完成后台 Job 标记完成 |
| 延展＋目标不存在、已结束或取消已生效 | 拒绝，不切到其他活跃任务，不新建替代 Run |

- 保留现有生效档取更严格者、同进程降档即时收紧、升档不放宽当前轮次/任务的规则。已有确认依据不因同一次降档被伪装成未批准，按现有执行端规则重验。
- AUTO_APPROVE 的累计阈值继续按会话计算，包括已结束 Run、已完成/失败/跳过项；拆调用、分段、重启不重置。重试保留原行，已有覆盖项不当新增操作重复计项。阈值不替代固定计划授权。
- 页面上下文、模型判断、输入参数和指定 Run ID 只表达请求对象，不构成批准。所有新建/延展受控入口执行现有对象范围、能力级别和授权校验。
- 提交结果明确区分已生成计划卡、已受理 Run、零变更、参数/批准错误；不得把受理回执描述为全部完成。真实逐步结果仍由 Run/Operation 查询提供。

### 6. 批准身份、版本与并发（Q5、Q9）

- 新建卡明确批准新建独立任务；两张不同的新建卡不因同会话自动合并。相同卡的重复确认由现有提案条件抢占保证只落一次，逻辑调用重放使用原回执。
- 延展卡绑定确定 Run、基础计划版本、逐项目标/参数/依赖及预览快照。不能在确认时选择另一 Run 或按最新版本重新解释批准。
- 主写事务内条件检查目标 Run 非终态、无已生效取消、基础版本一致，成功条件写后才落计划变更；检查 rowcount/等价持锁原子条件，不能只在工具或预览阶段 SELECT。
- 两张卡同基版本确认时，最多一张变更提交；另一张返回批准失效且不写入部分步骤。不同 proposal 的各自抢占不能替代同一 Run 上的版本竞争校验。
- 取消先提交则后续延展被拒绝；延展先提交则取消作用于已提交后的真实计划。取消不删除成功项、已提交领域 Job 或回执，确认不能清掉 cancel_requested 或复活取消任务。
- Worker 正常推进、后台 Job 状态更新、结果绑定及查询不提高计划版本。仅实际批准的参数/步骤变更推进版本；原计划与投影中的版本同步。
- 版本不符、目标结束/取消及旧格式缺批准信息是不可直接重试执行的批准失效；客户端即使重复点击旧确认，服务端也必须持续拒绝，直到显式重新预览并确认新卡。

### 7. 已有步骤分类与延展编译（Q6）

| 既有步骤 | 本次参数/依赖 | 处理 |
| --- | --- | --- |
| PLANNED/SUCCEEDED，既有目标相同 | 相同参数及等价既有依赖 | 覆盖复用，保留原 Operation 和位置 |
| PLANNED，既有目标相同 | 参数改变，既有依赖不变 | 重新确认后原位更新参数、快照与授权，保留 Operation 身份/位置/尝试历史 |
| SUCCEEDED，既有目标相同 | 参数改变 | 重新确认后追加新 Operation，原成功历史不改写 |
| FAILED/SKIPPED | 再次预览授权提交 | 沿用现有新授权步骤语义，不算已有覆盖；显式失败重试仍走原身份重试入口 |
| 无既有目标的创建项 | 名称、URL、内容相同 | 不做语义去重；仅同一逻辑调用/同卡防重 |

- 内部分类以真实动作、确定目标及规范化参数为依据。先识别覆盖的 Operation 和引用身份，再比较等价参数/依赖，不能把本批局部索引与 Run 全局索引直接当同一值比较。
- 编译器维护本批索引到既有/新 Operation 和 Run 步骤编号的对应，覆盖、原位修订、追加三类都参与映射；引用和 depends_on 同源重映射，消费者不接触各自平行序列。
- 新条目追加在原计划之后，旧条目和执行历史保留；纯覆盖不新增触发或执行副作用。保留实际新增/修订项数量回执，不把覆盖项算作再次执行。
- 不支持删步骤、重排或改变已有步骤依赖。新请求一旦要求改变这些关系就明确拒绝，不能接受后继续保留旧依赖而不告知；替换参数中的引用若引入新的既有依赖关系，同样不能静默通过。
- 编译时是 PLANNED、确认前已成功的步骤，在同一基础计划版本下按最终事务内真实状态重新分类：参数变更追加新操作，不能改写成功历史；快照与目标状态仍须重新验证，失效就拒绝。

### 8. 快照、提交原子性与失败记账（Q1、Q9）

- 提交/重新预览在事务内读取既有目标快照；确认时重验实际待写入步骤的快照；Worker 每步执行前继续最终重验。批准的对象版本与计划版本是不同检查，两者都保留。
- 既有目标的参数即使含输出引用，已知目标的快照仍须捕获/重验；尚未创建的目标不虚构快照，引用绑定后复用执行端已实现的完整校验与领域可见性检查。
- Run/Operation、plan_json 与版本、触发任务、ChatTurn 绑定、Proposal 成功状态/结果或 Effect 成功回执在入口主事务中原子提交。任一步骤失败，整次新建/延展回滚，旧计划保持原样。
- 自动提交继续在业务写事务处执行 ChatTurn 持久取消和执行身份门禁；Effect 前置 PLANNED 准入事务不等于业务已提交。成功 Effect 随主事务收口，失败不能持有伪成功回执。
- 提案应用失败继续主事务回滚后独立记账，条件保护不能覆盖另一请求已经提交的 APPLIED；保留稳定诊断及当前外层错误包装。不把所有失败事务塞入通用计划函数。
- 每步业务执行仍走既有受控 Operation 事务及独立失败事务，不在编译期执行领域动作。生命周期范围沿用：自动新建任务为独占绑定、已有任务为共享绑定，用户确认独立批准，不因抽象合并改变控制权。
- 坏计划在写入/推进路径拒绝，不能降级为空计划后覆盖旧步骤；展示保持既有可查询降级，不将损坏历史当成可重新批准的新内容。

### 9. 恢复、幂等与预算（Q4、Q6、Q9）

- 同一逻辑调用已提交的成功结果先于新参数校验、基础版本冲突和提交额度判断恢复。返回原 Run/Proposal/回执只是在读已发生事实，不能因任务结束重新建立执行。
- 新请求的 Effect 指纹涵盖业务语义：新建/延展意图、确定目标、适用的版本、完整计划项或重新预览来源。仅 items 相同不等于同一次新建/延展；同逻辑身份参数改变按既有指纹冲突规则拒绝。
- 复用现有工具预算与独立 5 次提交预算；一张新计划卡或一次真正提交仍按既有提交口径计数，计划项数受单批上限及授权阈值单独约束。已有成功提交回放不新扣提交额度，普通工具准入与字符预算继续走现有 module。
- WAITING_JOB/WAITING_USER、启动对账、Run/Job 唤醒和失败项重试继续复用既有机制。重启不重做 SUCCEEDED，不清 attempts、失败历史或后台 Job 关联，不添加第二套调度器。
- 新代码恢复旧持久 Effect 成功事实时读取原结果；若旧 checkpoint 的工具参数不满足新输入契约且没有可复用成功事实，必须明确阻止不兼容的新写入并保留已完成内容，走现有等待/停止/新问恢复路径，不能将旧参数默认为新授权。

### 10. 历史兼容与确定性重新预览（Q4、Q11）

- 兼容读取集中在计划 module 的旧格式 adapter。保留旧提案展示和回执、旧 Run 计划/Operation 参数解码；新请求和新持久提案只写新格式。
- 不批量改写历史 JSON，不新建并行执行结果表；新格式/基础版本/来源卡关联优先放在现有提案载荷与现有溯源事实中，本规格不预设新业务表或数据迁移。若实际实现确需结构变更，先核对必要性及现有迁移约束。
- 旧在途 Run 按原已批准参数继续，原 Operation ID、计划位置、版本、等待 Job、授权依据和结果保留；新增延展使用新批准契约。读取兼容不等于放宽旧待确认卡的执行权限。
- 旧待确认卡及失效卡可以查看/拒绝，但不得直接确认执行。提供计划专属重新预览公开入口；HTTP 与 Agent 薄 adapter 共用确定性服务，Agent 能按来源提案请求重新预览，不重新让 LLM生成或改写原计划内容。
- 重新预览校验来源卡类型/状态/归属和可解码性，保留原有效业务参数与依赖，更新快照及明确任务绑定和基础版本。旧资料按旧格式历史语义解码，例如旧 null 仍为省略；无法无歧义转换时返回错误或要求消歧，不能丢掉字段、改参数后自动继续。
- 新建/延展身份可确定时保留原意图；归属不明时返回需选择新建/确定 Run 的结果。原目标已结束、取消或不存在时不能偷偷改成新建，改换任务属于新的明确请求。
- 重新预览只创建新待确认卡，任何档位都不能借刷新直接执行。卡片/回执记录来源提案，原卡保留且仍不可直接执行；新卡显示最新批准内容，用户确认后才建 Run 或落延展事实。
- 在同一来源、同一明确请求意图和仍有效基础版本/快照下，重复/并发重新预览复用对应新卡或返回其已处理结果，不制造可被重复批准的多张卡。新的快照变化、版本变化或显式新请求需要新的预览，不能重用已失效卡。
- 重新预览幂等与来源关联落持久事实，跨重启不依赖前端 busy 状态或进程缓存。复用原 Effect/提案记账能力，必要关联只服务本次恢复能力，不扩成通用提案版本管理系统。

### 11. HTTP、Tool、结果投影与前端闭环（Q2、Q11）

- 保留现有 plan_batch_operations 能力入口及批量提案类型；更换其参数声明与后端解析契约，明确新建/延展意图。确定性重新预览经计划专属服务提供 HTTP/Agent 接入，复用现有提案确认/拒绝，不把批量重编译规则复制到路由或 Tool。
- Agent 能获得目标 Run 的真实 ID/计划版本及结构化状态，不能依赖页面挂载上下文猜测；返回缺参/歧义时追问，明确失败时停止重复确认旧卡。Tool 说明与 Prompt 同步实际参数和批准语义，沿用现有工具挂载范围。
- 结果仍兼容现有 run、plan_proposal、零变更与错误分类。批准卡输出能明确识别格式、任务意图/目标、版本、逐项参数/依赖、是否可直接确认及重新预览来源；前端不通过任意 JSON 强转猜测批准有效性。
- 新旧批量类型与批准状态使用后端可验证的契约；后端 schema 改动后同步 OpenAPI 与生成 TS 类型，不在前端再手写一份长期动作字段并集。通用提案 envelope 保持其他提案兼容，格式解码规则不散落多个页面。
- 前端保持现有计划卡结构、标题来源和状态层级，展示新建或延展哪个任务及计划版本。历史卡只读仍可核对参数/结果；旧卡、版本冲突或目标失效不保留可直接执行的确认按钮，但服务端才是最终执法者。
- 重新预览提供加载、失败、需消歧、新卡已生成及重复请求结果；失败保留原卡和输入，基础版本过期提示清楚。按钮禁用与请求回查配合现有查询失效，不用本地覆盖状态冒充真实 APPLIED。
- 保留任务进度、继续/重试/取消、等待原因和设置页操作历史；新卡确认后仍使用现有 Run 查询投影，旧成功回执不被格式升级降成无结果。
- 复用现有 shadcn/公共组件、错误消息映射和语义主题，不改全局设计体系。新增/修改文案同步中文英文；键盘、焦点、窄窗、大字号、多主题和 reduced motion 均纳入涉及控件的验收，不引入装饰动效。
- 参数、旧批准需重新预览、基础版本冲突、目标不可延展及不支持编辑具有稳定可区分原因；优先复用正确的既有错误码，新增时同步错误清单及双语 errors。保留外层 Proposal 应用错误的实际协议，不能只在内部返回新码而让前端丢失原因。

### 必须通过的行为矩阵

| 验收 | 可观察结局 |
| --- | --- |
| 三入口同源编译 | 相同计划经自动受理/确认/重新预览遵循相同动作参数、快照及引用规则，入口生命周期差异保留 |
| 输入约束 | 九动作保持能力；未开放动作、无关字段、显式 null、坏引用、超 50 项整体拒绝，无 Run/Operation 部分落库 |
| schema 校验器 | 原动作条件校验及字段约束可通过真实入口触发；引用仅延期确实未就绪部分，最终完整校验不被绕过 |
| 新建/延展分流 | 新建三档规则和会话累计阈值不变；AUTO_APPROVE 未确认 Run 的新增/改参改为出卡；等待态也先确认 |
| 同卡/不同卡并发 | 同卡最多一次写入；两张同基版本延展卡最多一张变更提交，另一张失效且旧计划无部分追加 |
| 执行进度交错 | PLANNED 在确认前变成功时不覆盖历史；进度/Job 变化不升计划版本；实际参数改变仍重验快照 |
| 取消/确认交错 | 取消先提交则延展不落库；确认先提交则取消按真实新计划收口，成功项与已提交 Job 保留 |
| 延展分类/映射 | 覆盖不重做、待执行修订保身份、成功修订追加；覆盖/替换/新增混合批次引用和依赖指向真实 Operation |
| 不支持编辑 | 删除、重排、改变既有依赖明确拒绝，参数和依赖不被静默部分接受 |
| 提交/失败原子性 | 主事务失败时版本/计划/Operation/绑定/Job/成功回执整体回滚；独立失败诊断正确且不覆盖并发成功 |
| 中断/预算 | 业务成功而 checkpoint 未完成时返回原事实；Effect 新语义指纹可区分任务；恢复不重扣提交、不重做成功步骤 |
| 新旧兼容 | 旧成功回执可查、旧在途 Run 真重启可恢复、旧待确认直接确认持续拒绝；不兼容旧 checkpoint 不产生新副作用 |
| 重新预览 | 页面对话共用能力、参数保留、真实快照/任务版本重读、先消歧再新卡；重复/并发/跨重启不产生重复批准 |
| 前端闭环 | 新旧类型展示、失效隐藏确认、重新预览成功/失败/忙/消歧、历史回执与任务控制可用，中文英文一致 |
