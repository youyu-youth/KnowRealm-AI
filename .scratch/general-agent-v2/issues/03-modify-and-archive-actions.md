# 03 — 单对象修改与归档动作（执行前快照机制）

**What to build:** 落地「执行前快照」机制并接入首批 L1 修改与归档动作：课程修改、课程归档 / 恢复（归档写路径首次落地，历史推迟决策收口）、资料条目重命名 / 归类 / 归档 / 恢复。每个动作确认卡展示 before/after 预览（读快照）；确认前用户手动改过同一对象则旧提案失效（稳定错误码），不覆盖新修改；快照同时作为 06 票 Undo 的补偿数据。用户可演示：「把课程 X 改名为 Y」→ 确认卡 before/after → 确认生效 → 回执可跳转；预览后自己在页面改了名 → 确认失败并提示重新确认。

**实施约束:** 实施决策见 [spec](../spec.md) 决策 12、14、16（快照由后端在提交时同事务读取固化，模型不提供；不给业务表加 version 列；updated_at 微秒精度＋before 值＋级联清单即版本依据；ORGANIZE 类型不迁注册表、只补纪律）。

**Blocked by:** 01 执行事实地基与操作历史。

**Status:** ready-for-agent

- [ ] 注册项快照声明扩展：提交时后端同事务固化 snapshot_json（直接目标 updated_at＋修改动作 before 值＋级联影响清单字段）；快照形状按动作声明、进判别校验
- [ ] 执行前重验：应用器比对快照与当前态（updated_at / before 值 / 影响清单），不匹配 → 稳定错误码失效（旧批准作废、需重新预览授权）；正常派生索引维护不算变化
- [ ] updated_at 纪律防线：课程修改 / 归档 / 恢复与条目重命名 / 归类 / 归档 / 恢复全部写路径在既有测试中断言 updated_at 变化（spec 决策 12 显式不变量：所有领域写路径必须维护 updated_at）
- [ ] course.update（L1）：复用课程更新领域校验链（场景 / 阶段或深度条件校验同源），HTTP 与应用器共用事务内核心
- [ ] course.archive / course.restore（L1）：新归档写路径（领域端点＋Agent 动作）；既有 ARCHIVED 读取护栏三道闸门零改动；spaces 手动归档 / 恢复菜单入口一并补（同一端点）
- [ ] library_item.update（L1，标题 / 归类；收藏不接入）＋library_item.archive / restore（L1）：复用 lifecycle 既有领域核心＋补快照
- [ ] ORGANIZE 应用器补纪律：执行前重验＋before 快照进结果投影（类型不迁注册表，旧待确认提案沿用现行确认路径）
- [ ] before/after 确认卡泛化（复用既有操作提案卡扩展），修改类动作预览完整呈现旧值 / 新值；回执卡呈现修改结果
- [ ] 默认档落提案（现状链路）；02 已上线时自动档按 level 继承直执行（注册表零改动验证）
- [ ] 新增错误码登记＋zh/en 双语同步；api-types regenerate
- [ ] 门禁全套过（后端 pytest / ruff / pyright、前端 vitest / lint / build、OpenAPI --check）

**用户真机验收（单列，不代勾）：**

- 真实会话完成一次课程改名与一次条目归类：确认卡 before/after 准确，确认后页面即时可见。
- 预览后在页面手动修改同一对象，再点确认 → 明确失败原因（目标已变化），重新确认后按新值执行。
- 课程归档后课程不再接受新资料（既有护栏）；恢复后恢复正常；spaces 菜单手动归档入口可用。
