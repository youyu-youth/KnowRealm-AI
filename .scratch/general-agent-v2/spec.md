# 通用 Agent 第二阶段：三档授权、修改与批量整理（spec）

Status: ready-for-agent
定稿依据：开发计划文档 + 设计-4 采纳版 + ADR-0026 + 2026-09-22 grill 三轮 Q1～Q22 全部用户确认（决策记录见 [grill.md](grill.md)）。

## Problem Statement

第一阶段只交付了默认档下的两个可靠单步写动作（建课程、加文本记录），用户仍只能逐条确认：批量整理的摩擦没有降低；修改、归档、软删除、跨课迁移这些高频治理动作没有受控入口；冲突后的任务不能等待用户、跨重启接续；自动执行缺少授权依据、执行历史与有限撤销。后续阶段（多资料长任务、条件式生态扩展）全部压在同一批地基上——执行事实、授权、版本、批次推进与恢复——这批地基必须在放大能力面之前落稳。

## Solution

1. **三档授权**：请求批准（默认，与现行提案规则零行为变更）/ 帮我批准 / 完全访问；档位只决定「落提案等确认」还是「校验通过即执行」，执行端确定性分流，任何档位不改变 Memory、内容审核与外发边界（ADR-0026）。
2. **修改与生命周期动作**：课程修改 / 归档 / 恢复、资料条目重命名 / 归类 / 归档 / 恢复、Record 软删、课程软删（删除编排收拢）、Record 跨课迁移——全部注册进操作注册表，操作快照一份三用（确认卡预览、执行前重验、Undo 补偿数据）。
3. **执行事实模型**：新增 Run 与 Operation 持久化两表，Operation 自始为执行事实唯一源，提案结果字段降级为单向投影缓存；批次由「Run ＋ JobRunner 内 AGENT_RUN 触发 job」推进，job 是无状态触发器、不承载任务状态。
4. **批量计划卡**：整卡一次确认绑定对象集合＋参数＋计划版本；「帮我批准」档 10 目标＋10 写操作阈值；部分失败独立继续、依赖阻塞；等待用户与跨重启接续。
5. **有限 Undo 与重试**：快照补偿、批次按依赖逆序补偿、原操作身份自动重试 ≤2 次。
6. **操作历史与审计**：设置页操作历史分区、查询 API、模式切换审计、显式清理（删除聊天不删除任务历史）。

## User Stories

**授权模式**

1. 作为学习者，我想在设置页选择全局默认授权档（默认=请求批准），让新会话继承我的信任偏好。
2. 作为学习者，我想在会话内临时切换授权档（按会话记忆，重启应用回落全局默认），处理不同敏感度的任务。
3. 作为学习者，默认档下我的体验与第一阶段完全一致：所有写操作先出确认卡，未确认零业务事实。
4. 作为学习者，切到「帮我批准」后，单对象创建与可逆修改自动执行并给回执；删除等高风险操作仍逐项强制确认。
5. 作为学习者，切到「完全访问」后，除禁止项外全部自动执行并给回执，我不需要逐条点确认。
6. 作为学习者，会话中途降档后，后续动作重新检查授权，不沿用旧自动授权；升档不自动执行积压的待确认提案。
7. 作为学习者，自动执行的操作回执上能看到授权依据（当时档位、触发指令原文、时间），出问题可以追溯。
8. 作为学习者，模式切换本身留有历史记录，任何档位审计链不断。
9. 作为学习者，任何档位下，长期 Memory 写入、AI 总结与学习资产采纳、外发同意仍按原有确认规则执行。

**修改与生命周期**

10. 作为学习者，我想让 Agent 修改课程信息（名称、场景、阶段/深度、类型、说明），确认卡展示 before/after 预览，确认后才生效。
11. 作为学习者，我想让 Agent 归档课程并在之后恢复；归档后课程不再接受新资料（沿用既有读取护栏）。
12. 作为学习者，我想让 Agent 重命名资料条目、修改归类、归档与恢复条目，每个动作都有 before/after 预览。
13. 作为学习者，我在 Agent 提案未确认前手动在页面修改了同一对象，旧提案应失效并要求重新预览，而不是覆盖我的新修改。
14. 作为学习者，我想让 Agent 软删除记录或课程（高风险操作，任何档位下帮我批准档仍逐项确认）；删除的级联影响（如课程下的记录清单）在确认卡上完整呈现。
15. 作为学习者，批准删除课程后、执行前若课程新增了记录，旧批准失效，需要重新预览确认，新增记录不会被悄悄纳入删除。

**跨课迁移**

16. 作为学习者，我想让 Agent 把记录迁移到另一门课程：记录内容与记录级资产（总结、知识点、Todo、复习资料）随记录移动。
17. 作为学习者，迁移后原课程的概念、历史作答、已完成测试与学习证据保留历史归属，旧课程的历史测试仍可回看。
18. 作为学习者，迁移不会给目标课程继承掌握度，也不会按概念同名自动匹配；目标课程的当前概念关联重新校验。
19. 作为学习者，记录有正在进行的处理任务（如总结生成中）时，迁移被明确拒绝并告知等待处理完成。
20. 作为学习者，迁移错了可以撤销（反向迁移），同样经过完整领域校验。

**批量与计划卡**

21. 作为学习者，我想说「把这些条目都归到课程 X」，Agent 给出一张计划卡：逐项列出目标、参数与计划版本，整卡一次确认。
22. 作为学习者，「帮我批准」档下，不超过阈值的批量自动执行并给批次回执；超阈值仍出计划卡确认。
23. 作为学习者，计划修改（增删对象、改参数）后计划版本递增、需要重新确认；执行中重规划新增目标超出已批准集合时升回确认（完全访问档亦然）。
24. 作为学习者，批次中单项失败不回滚整个批次：独立项继续、依赖项阻塞，最终如实呈现部分完成。
25. 作为学习者，批次遇到冲突可以保留已成功结果、等我处理完冲突再继续，重启应用后仍能接续，不重做已成功项。
26. 作为学习者，我可以随时取消任务：取消后不再新增动作，已提交结果保留，取消不被冒充为撤销。

**Undo 与重试**

27. 作为学习者，重命名、归类、归档、恢复、跨课迁移、条目删除这些动作可以撤销；撤销前检查版本与依赖，我之后的修改不会被撤销覆盖。
28. 作为学习者，不能撤销的动作（记录软删、课程删除、课程级联删除）明确告知原因，而不是默默失败。
29. 作为学习者，瞬时故障自动有限重试；失败项可以手动重试且不会重复成功部分；重试沿用原操作身份，我想「再来一次」时才是新操作。
30. 作为学习者，批次撤销按依赖逆序补偿，逐项结果如实呈现。

**历史与审计**

31. 作为学习者，我想在设置页看到操作历史：任务、逐项操作、模式切换，可按状态过滤。
32. 作为学习者，删除聊天会话不会删除关联任务历史，界面明确说明；我可以用显式入口清理已结束任务的历史（同时失去对应 Undo 与回查）。
33. 作为学习者，清理后消息流中的旧回执卡降级为「历史已清理」占位，消息本身不被删除。
34. 作为学习者，断线或重启后，我能通过持久化查询恢复任务状态视图，不依赖 SSE 仍在连接。

**开发者**

35. 作为开发者，我想通过声明式注册接入新写动作（快照 schema＋应用器＋结果投影），公共执行流程零改动、零领域专属分支（AST 防线延续）。
36. 作为开发者，我想让 HTTP 路径与 Agent 应用器共用同一事务内业务核心（课程创建先例），课程删除的掌握度重算编排同样收拢，路由换用后既有测试零改动通过。
37. 作为开发者，我想复用 JobRunner 的声明式执行体模式实现 Run 推进 worker，不引入第二套调度器或运行时编排器。
38. 作为开发者（未来的自己），我想在崩溃、超时、重启后凭 Operation 行查明每个动作是否已执行、结果如何、重试了几次。
39. 作为 Agent（模型），我的工具语义恒为「完成这件事」，是否需要确认由后端档位决定，工具名称与描述不随档位改变。

## Implementation Decisions

以下决策全部来自 grill Q1～Q22 定稿，实施不再开放重议；与设计-4 / ADR-0026 冲突时以本文为准并显式提出。

**执行事实模型（Q7/Q14/Q22）**

1. 迁移 0030：新增 `agent_runs`、`agent_operations`、`agent_activity` 三表；`agent_proposals` 的 proposal_type CHECK 一次改造为「存量五类型白名单（ORGANIZE / MEMORY / RESEARCH_INGEST / COURSE_CREATE / TEXT_RECORD_ADD）＋ `OP_` 前缀通配」——本阶段及后续新操作类型统一落 OP_ 命名空间，不再逐动作整表重建；类型执法仍在判别 schema 注册表（未注册类型创建即拒），DB CHECK 只是纵深防御（整表重建与 `legacy_alter_table` 防 FK 改写先例沿用）。动迁移先全库 grep user_version 硬编码断言并同步。
2. `agent_operations` 核心列：id、run_id（可空，单步操作不建 run）、proposal_id（可空，关联审批）、action、level、target_type/target_id、payload_json（判别 schema）、snapshot_json（执行前快照）、authorization_json（授权依据：档位＋触发指令摘录＋消息引用——直执行与 run 内执行统一落列，单步无 run 时授权事实的唯一载体，ADR-0026 审计要求）、status、attempts、attempts_json（逐次尝试错误历史）、result_json、error_code、undo_of（自引用可空）、undone_by、created_at/updated_at/finished_at。操作状态机：PLANNED → SUCCEEDED / FAILED / SKIPPED / CANCELLED——不持久化 RUNNING，每个操作一个原子事务（崩溃=未发生，可安全重试）。
3. `agent_runs` 核心列：id、session_id（仅溯源，可空）、auth_mode、instruction_text（触发指令原文）、proposal_id（批次审批引用，可空）、status、plan_json（对象集合＋逐项参数）、plan_version、waiting_reason（可空）、cancel_requested、created_at/updated_at/finished_at。Run 状态机：RUNNING / WAITING_USER / COMPLETED / PARTIAL_COMPLETED / FAILED / CANCELLED；`WAITING_JOB` 枚举预留、本阶段不启用（第三阶段等待后台任务用）。终态判定：全部成功=COMPLETED；存在失败或跳过项且无阻塞依赖=PARTIAL_COMPLETED；系统性故障或取消=FAILED / CANCELLED。
4. Operation 自始为执行事实唯一源：第一阶段两类动作的确认执行回接写 operation（run_id 空）；自动档直接执行与批次推进同。`agent_proposals.result_json` 降级为 operation→proposal 的单向投影缓存（确认时由 operation 结果投影回写），旧提案接口零变化；存量 APPLIED 提案不回填 operations，操作历史仅展示新纪元，旧回执经既有提案查询仍可达。
5. Run 代码落 agent 模块新子包（模型 / 服务 / 推进 worker / 查询分层）；提案框架继续留在 library 域不动；依赖方向 agent → library / course / capture / record，无环；「公共执行流程零领域分支」纪律由既有 AST 防线延续覆盖新子包。

**批次推进（Q14/Q15）**

6. ProcessingJobType 新增 AGENT_RUN：job 是无状态触发器（input 仅携带 run_id），不承载任务状态；同一 run 至多一个活动触发 job（领取守卫判定）；Run 状态是唯一事实源。推进 worker 逐 operation 原子执行，每步前重检取消、授权与版本（Q10）；推进 worker 只认 RUNNING。
7. 唤醒仅由显式动作触发（用户继续指令、失败项重试、冲突项解决、取消），唤醒走原子抢占（RUNNING 守卫，提案确认先例），不自动猜测 WAITING_USER 可否继续。重启恢复：启动扫描 RUNNING 且无活动触发 job 的 run 重投触发（JobRunner recover_interrupted 先例）。
8. 部分失败语义（Q4）：独立项继续；依赖失败项的后续步骤置 SKIPPED；授权失效、取消或系统性故障停止后续推进；普通单项失败不回滚整个批次。

**授权（ADR-0026 / Q3 / Q9 / Q17）**

9. 授权档位枚举 REQUEST_APPROVAL / AUTO_APPROVE / FULL_ACCESS。全局默认落 settings.json 偏离项（默认档不写键，learner_memory 外发开关先例）；会话档位为前端按会话内存（web_search 开关先例），重启应用回落全局默认（安全方向）；跨重启接续按 Run 固化的授权依据＋每步重验，不回放会话档位。
10. 运行时上下文新增授权档位字段；操作提交路径分流：默认档＝落提案（现状零变化）；AUTO_APPROVE＝L0/L1 自动、L2 不超阈值自动、超阈值出计划卡、L3 逐项强制确认；FULL_ACCESS＝除禁止项外全自动（固定计划对象集合外新增目标仍升回确认）。禁止项（物理删除、任意 SQL、任意路径写、宿主 Shell）任何档位不暴露。
11. 自动执行在单事务内写 operation 与业务结果；失败走独立小事务落 FAILED＋稳定错误码（提案 _mark_failed 先例）。回执记录档位、触发指令原文与时间。每轮操作类预算上限 5 不变（提案与直接执行同计，超限拒绝不截断）；「帮我批准」批量阈值为同一任务直接业务目标 ≤10 且写操作 ≤10（计入已完成项，拆调用 / 分段 / 重启不重置；同一 operation 重试不重复计项）。

**版本与快照（Q8 / Q16）**

12. 操作注册项扩展「执行前快照」声明：直接目标固化 updated_at（微秒精度）＋修改动作的 before 值；级联影响固化清单快照（如课程删除＝当前 record id 集合与计数）。执行前重验：直接目标 updated_at 不匹配、或影响清单出现实质差异 → 稳定错误码失效（旧批准作废，需重新预览授权）；正常派生索引维护不算新增业务目标。快照一份三用：确认卡预览投影、执行前重验依据、Undo 补偿数据。不给业务表加 version 列；快照机制的显式不变量＝**所有领域写路径必须维护 updated_at**（正文编辑已有真版本列先例，课程 / 条目 / 记录以 updated_at＋before 值双保险承载，领域日后引入自身版本列可平滑替换比对依据），工单 03/04 对快照覆盖的写路径以断言钉住。
13. 计划卡＝批次授权载体：新提案类型 OP_BATCH（OP_ 命名空间，决策 1），payload 携带对象集合、逐项参数与 plan_version；计划修改后版本递增、重新确认；整卡一次确认即批次授权。

**动作清单（Q20）**

14. 本阶段注册动作：L1＝course.update（复用课程更新领域校验）、course.archive / course.restore（新归档写路径；ARCHIVED 状态与三道读取闸门已在，属历史推迟决策的显式收口）、library_item.update（标题 / 归类，收藏不接入）、library_item.archive / library_item.restore；L2＝record.move_course、资料条目批量归类 / 归档（计划卡编排既有 L1 动作，不另立动作类型）；L3＝record.soft_delete、course.soft_delete。Record 重命名无领域端点，登记缺口、本阶段不做。每动作＝一个注册项＋一个薄工具（第一阶段模式不变）。
15. 课程删除编排收拢：软删（含级联软删记录、取消非终态任务、录音会话脱钩）＋掌握度重算＋consumer 重试编排收拢为 course 域应用函数，HTTP 路由与 Agent 应用器共用（create_core 先例）；路由换用后既有路由测试零改动通过＝收拢验收锚点。
16. ORGANIZE 提案类型不迁操作注册表（兼容零 churn）；其应用器补执行前重验与 before 快照（快照进结果投影）；旧待确认提案沿用现行确认路径、不进自动执行扫描（Q12）。MEMORY 与 RESEARCH_INGEST 零改动。

**跨课迁移（Q2 / Q11 / Q19）**

17. 新领域服务 move_cross_course（HTTP 与 Agent 共用、事务内）：修改 record.course_id、重建搜索索引、重校验目标课程存在且 ACTIVE；该记录存在非终态处理 job 时以稳定错误码拒绝（等待处理完成再迁移）。
18. 不触碰清单：quiz 存量 concept_id 绑定、quiz_test_items、learning_events / learning_evidence（course_id 写入时固化＝历史归属，语义天然成立）、record_concepts 行（读取期按 record 所属课程过滤防污染，移回课程即复现）。习题主概念「同课程 CONFIRMED」校验只管新绑定、不回溯存量。知识点 / 总结 / Todo / 复习资产挂 record_id 天然随走。迁移快照存原 course_id，Undo＝反向迁移（过全部校验）。

**Undo 与重试（Q5 / Q10）**

19. Undo＝新的受控补偿操作（undo_of 链、undo 前重验版本与依赖、保留原执行历史）：首批支持＝重命名、归类变更、归档 / 恢复、跨课迁移、条目软删（回收站恢复链已可靠）；记录软删、课程软删与课程级联删除不提供 Undo（明确原因）。入口＝回执卡 / 操作历史按钮（UI 显式动作即用户授权，直接建补偿 operation）与经 Agent 的 undo 工具（走三档授权）。批次 Undo＝按依赖逆序补偿、保留逐项结果；取消不冒充撤销。
20. 重试：瞬时故障（如 SQLITE_BUSY、临时 IO）在原 operation 身份下自动重试 ≤2 次，每次重验授权 / 版本 / 取消；参数错误、领域拒绝、版本冲突、权限失效不自动重试；未知结果先对账——operation 行与业务写同事务，行在＝已执行、行不在＝未发生（SQLite 单写者下的干净锚点）；手动重试沿用原身份（attempts 递增），用户明确要求重复执行才创建新 operation。

**历史、审计与清理（Q13 / Q18 / Q21）**

21. 查询 API：GET runs（分页 / 状态 / 会话过滤）、GET 单 run 详情（含逐 operation）、GET activity（模式切换审计流）；清理＝按终态 run 删除历史＋批量清理已结束任务（活动任务先结束或取消）。默认永久保留、无自动过期；runs / operations 在 SQLite 内随全量导出与备份自动包含。清理后消息流旧回执卡降级「历史已清理」占位，消息不删。
22. `agent_activity` 记录模式切换（from / to / 作用域 / 会话 / 时间）。设置页新增「Agent 自动化」分区（全局默认档三选一）与「操作历史」分区（run 列表展开逐 operation＋模式切换审计＋清理入口）。V1 不做按对象聚合的历史视图。删除聊天会话不删除关联 run / operation / 审计（界面说明）。

**SSE 与前端**

23. 零新 SSE 事件类型：完成载荷新增直接执行回执键；计划卡复用既有提案就地卡泛化模式（Settled / Actionable 先例）；断线与重启经持久化查询恢复状态视图（第一阶段先例）。聊天右栏新增授权模式开关（web_search 开关位置先例）。新增文案 zh / en 同步；新增稳定错误码进清单并同步双语。

## Testing Decisions

测试只断言外部行为（表行与状态、业务对象存在性、回执载荷、幂等结果），不断言注册表内部结构或私有函数；全部复用既有测试缝隙，不新建缝隙：

- **工具层**：直调工具函数（绑定统一运行时上下文）断言分流行为（默认档落提案 / 自动档直执行回执 / L3 恒确认 / 预算上限）——先例：操作工具往返测试。
- **确认与应用层**：经既有提案确认端点断言 operation 回写、业务结果、双确认 409、快照失效路径（预览后手动改对象 → 确认失败稳定错误码）——先例：library 提案测试。
- **执行事务核心复用回归**：课程删除编排收拢后，既有课程删除路由测试零改动通过；迁移服务既有归类 / 生命周期测试零回归。
- **Run 推进**：JobRunner 测试缝隙（冻结时钟推进）断言逐项推进、部分失败、取消停止、重启重投、等待与唤醒抢占——先例：test_job_runner。
- **前端**：MSW mock 新端点，断言计划卡确认流转、回执卡、操作历史分区、清理降级占态——先例：ChatOperationProposalCard 测试。
- **故障场景**（验收票集中）：降档重验、超阈值计划卡、旧提案不进自动执行、崩溃后 operation 对账、重启续跑不重做。
