# 03 真机反馈：双任务被串行安排并耗尽共享额度

日期：2026-10-22。实施基点：`621033f21dc4eedc728bb4ffc406cc73d9246db0`。

## 已核实的问题与规格判断

用户真实桌面对话的根轮次 `278938c4-dcd2-4ab6-a1e4-cc4f9eacc6ac` 只创建了一个子任务 `40138d62-be31-4a33-a9e8-530ca51a823f`。通用助手先委派任务一，等待其完成后再请求委派任务二；第一次委派和子助手五次检索已消耗全部六次准入，第二次委派返回 `TOOL_CALL_LIMIT`，没有创建第二个任务。旧任务与用户资料保持原样。

03 规格要求父子共享六次工具额度、每轮最多两个子任务，支持主助手在同一条模型回复中发出两个独立 ToolCall。六次上限拦截符合规格；本次明确要求同时分工却采用串行安排、把共享工具耗尽解释为只能委派一个，不是双任务并行验收通过。首期仍由通用助手决定委派，不新增前置分类模型或编排平台。

## 修复计划与范围

1. 在具备本地委派工具的 general 挂载上下文中补充分工指引：两个独立任务在同一条模型回复中发出两次 `delegate_knowledge(task)`，每次仅一个任务，先安排再等待。FREE 与 knowledge 不注入此能力说明；有真实依赖的任务保留顺序处理。
2. 澄清父子共享额度，修正“每个助手可检索六次”的误导。子任务冻结输入追加共享额度说明，优先一至两次检索后以已有证据和缺口形成报告；使用少量核心词、未命中时删减关键词，避免不断拼入新子主题。这不是新增每子任务两次的硬上限。
3. 委派被共享预算拒绝时，保留原 `TOOL_CALL_LIMIT`，附准确原因，不误报为只能委派一个或权限不足。预算准入、幂等、取消、最多两子任务、双槽和恢复路径保持。
4. 普通/研究提示版本升为 v36/v37，工具说明与冻结子输入变化对应图版本 v14，按既有不兼容等待处理旧在途轮次；不重新执行旧用户任务。

能力入口复用原 Tool、登记 Service、JobRunner 与恢复映射；目标、scope、授权和外发同意由原快照派生。此次不新增 API、schema、依赖、批量委派工具或调度循环。
