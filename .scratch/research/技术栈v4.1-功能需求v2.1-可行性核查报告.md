# 技术栈 v4.1 × 功能需求基线 v2.1 可行性核查报告

> **调研日期**：2026-08-17
> **调研方式**：3 个并行核查代理对照**官方一手来源**（PyPI / 官方产品文档 / 官方仓库 / Microsoft Learn / MDN / chromium.org 等）逐条验证技术断言；本文汇总其结论并叠加"需求→技术覆盖矩阵"分析。
> **回答的问题**：① 技术栈 v4.1 的技术要求能否覆盖功能需求基线 v2.1 的功能？② 这些功能实际上真的可以实现吗？

---

## 0. 结论摘要（TL;DR）

**可以实现，无方向性证伪。** 全部功能模块在技术栈 v4.1 中均有承接方案，三大技术域（录音链路 / AI+数据栈 / 前端桌面栈）的核查均以官方一手来源支撑"可行"判断。但核查发现：

1. **1 个架构级冲突（必须产品决策）**：腾讯云 ASR 本地直传（base64）单文件上限 **5MB**——不仅 3 小时录音（~30+MB）超限，**连一节 45~90 分钟的常规课堂录音（11~20MB）也超限**。"转码后直接本地提交 ASR"的隐含假设不成立，必须二选一：引入 COS 上传（走 URL 方式）或**按录音分片逐段识别后拼接时间戳偏移**。详见 §2。
2. **3 个必须进 S0 POC 的实测项**（依赖间接行为或无官方背书的缝合点）：3h 后台录音稳定性、sqlite-vec 在 PyInstaller×Windows 下的加载、PyInstaller 重栈打包指标。
3. **约 10 处文档勘误**（版本事实与表述偏差，见 §5）：Node 22 LTS 已结束须改 24、ffmpeg 已到 9.x、`ES_AUDIO` 未文档化、shadcn 实为三种底座且 Base UI 已成默认等——均为修正级，不动摇选型。

## 2. 架构级发现：ASR 上传通道与"本地优先"的冲突（需拍板）

### 2.1 事实

腾讯云录音文件识别 CreateRecTask 两种提交方式（官方文档 [cloud.tencent.com/document/product/1093/37823](https://cloud.tencent.com/document/product/1093/37823)）：

| 方式 | 限制 | 适用 |
|---|---|---|
| URL 方式（SourceType=0） | 时长 ≤5h、文件 ≤1GB，**须公网可下载 URL** | 大文件 |
| 本地直传（SourceType=1，base64 进 body） | **数据 ≤5MB** | 短音频 |

ogg-opus@16kHz 按常见 24~32kbps 码率估算：**10 分钟 ≈ 1.8~2.4MB；45 分钟 ≈ 8~11MB；1 小时 ≈ 11~14MB；3 小时 ≈ 32~43MB**。

即：PRD 设想的"转码后本地直接提交 ASR"只对 ≤5MB（约 20 分钟以内）的音频成立。**一节标准课堂录音（45~90 分钟）就超限**，不是 3 小时长录音才触发的边角案例。

### 2.2 与红线的冲突点

- 红线 #12（数据外呼白名单）允许"ASR API 调用"——音频数据交给腾讯做识别本身在白名单内；
- 但 **URL 方式要求先把文件放到公网可下载存储（如 COS）**，这引入了"数据落在第三方对象存储"的环节，超出"API 调用"的字面范围，且与 PRD §4.3.1 "**无上传环节**"的硬约束表述直接矛盾（该表述原意是不上传云端存档，但 ASR 提交环节事实上需要上传）。

### 2.3 候选方案（供拍板）

| 方案 | 做法 | 代价 | 红线 #12 影响 |
|---|---|---|---|
| **A. 分片逐段识别（推荐优先评估）** | 录音本就按 5~10 分钟分片；每片转码后 ≤2.4MB 走本地直传（SourceType=1），CreateRecTask 逐片提交、DescribeTaskStatus 轮询，**时间戳按分片起始偏移量拼接**；导入音频同样由本地 ffmpeg 切成 ≤5 分钟段 | 时间戳偏移拼接逻辑（工程量可控）；任务数增多（接口限频 20 次/秒，任务并发未见上限条款） | 无新增出网通道，语义上仍是"ASR API 调用" |
| B. COS 上传 + URL 提交 | 文件上传腾讯 COS（同账号），CreateRecTask 传 URL | 引入 COS 依赖 + 用户须多配一套 COS 密钥；数据经对象存储 | 需扩白名单（"ASR 链路含 COS 上传"），与 #55"无上传环节"表述冲突，需 PRD 改写 |
| C. 混合 | ≤5MB 直传、>5MB 分片 | 两条路径两套测试 | 同 A |

**建议**：方案 A 与现有"录音分片"设计天然同构（分片本来就是架构的一部分），不引入新外部依赖；但**每片识别结果之间无跨片语言模型上下文**（词级热词仍生效），对专有名词跨片一致性略有影响，需在 S0 POC 用真实课堂音频验证拼接效果。此问题应记入 PRD §11 待确认清单（新增 Q16），并在 S0 POC 中实测。

## 3. 必须进 S0 POC 的实测项（风险按严重度排序）

### 3.1 【高】3h 后台录音稳定性——依赖间接行为，无官方开关兜底

- **有利证据**：Chromium intensive throttling 官方豁免规则——存在 live MediaStreamTrack（麦克风流开着）的页面只降到普通 Throttling 级（约 1 次/秒），不进 intensive（1 次/分钟）[developer.chrome.com/blog/timer-throttling-in-chrome-88](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)；`MediaRecorder.start(timeslice)` 的 `dataavailable` 由媒体管线驱动，非 JS 定时器；WebView2 `TrySuspend` 需宿主**主动**调用（最小化不会自动挂起渲染进程）[learn.microsoft.com/.../corewebview2.trysuspendasync](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2.trysuspendasync)。
- **不利证据**：Tauri 官方 Webview 文档自述默认挂起策略可在隐藏/最小化约 5 分钟后"节流定时器甚至卸载 view"，而 `backgroundThrottling` 开关 **Windows 不支持**（仅 iOS 17+/macOS 14+）[v2.tauri.app/reference/javascript/api/namespacewebview](https://v2.tauri.app/reference/javascript/api/namespacewebview/)；WebView2Feedback #413 有最小化恢复异常报告。
- **POC 要求**：最小化 / `window.hide()` / 锁屏 三工况 × ≥3h 实测；**分片落盘挂 `dataavailable` 即写盘**（管线驱动），不要依赖长 `setInterval` 触发 stop；录音期间窗口隐藏（托盘常驻）优于最小化。

### 3.2 【高】sqlite-vec × PyInstaller × Windows——无官方背书的缝合点

- vec0 `float[1024]`、KNN（`WHERE embedding MATCH ? AND k = 5`）、官方 Python 包 `sqlite_vec.load()` 均证实（[github.com/asg017/sqlite-vec](https://github.com/asg017/sqlite-vec)）；
- 但：官方**无 async 集成文档**（aiosqlite 有 `load_extension()` API、SQLAlchemy 有 connect 事件通道——组装方案可行但无官方背书）；**无 PyInstaller 打包指南**（社区通例 `--add-binary vec0.dll`）；**Windows pip wheel 为 MinGW 编译，与 CPython 自带 sqlite3.dll 有真实加载失败案例**（官方 issue #13 / #45）。
- **POC 要求**：S0 冒烟必须包含"PyInstaller 冻结包内 Windows 加载 vec0 并执行 KNN"；备选路径：官方 release 的 loadable 二进制 / MSVC 自编译 / pysqlite3。

### 3.3 【中高】vec0 软删/范围过滤的建模选型

- metadata 列可直接进 KNN WHERE（比较符 =,!=,>,>=,<,<=，≤16 列；**布尔仅 =/!=**）；partition key 仅 = 预过滤（≤4 个）；**`deleted_at IS NULL` 的 NULL 语义未在 metadata 过滤操作符中列明**——不能想当然地把软删过滤塞进 vec0。
- **推荐模式**（与 `.claude/rules/langchain-langgraph.md` §10 封装层设计一致）：**KNN 取超额候选（如 k×3）→ join `semantic_embeddings` 业务表过滤 `deleted_at IS NULL` 与 course_id/record_id → 截断到 k**；或建模 `is_deleted` 布尔 metadata 列。勿让 partition key 承担软删语义。

### 3.4 【中】PyInstaller onefile 冷启动与杀毒误报——官方承认的现实问题

- onefile 每次启动自解压到临时目录（官方文档明说）[pyinstaller.org/en/stable/operating-mode.html](https://pyinstaller.org/en/stable/operating-mode.html)；误报根因官方 issue #6754 承认，缓解 = 最新版 + `--noupx` + 代码签名 [github.com/pyinstaller/pyinstaller/issues/6754](https://github.com/pyinstaller/pyinstaller/issues/6754)。
- onedir 冷启动更快、误报更少，但 Tauri externalBin 是单文件机制，迁 onedir 需改 resources 目录方案（额外工程量）。维持 v4.1"onefile + S0 冒烟回填"的决策合理，CI 应加代码签名。

## 6. 对"实际上真的可以实现吗"的直接回答

- **MVP（Wave A/B）**：可以。学习闭环主干（录音/导入→转码→ASR→总结 HITL→知识点/习题/Todo/导出→AI 问答 SSE）每一环都有一手来源支撑，前提是 §2 的 ASR 通道先拍板、§3 的三项 POC 通过。
- **P2+（RAG/Learning Brain）**：可以，但 sqlite-vec 的三个缝合点（async 集成、PyInstaller 加载、软删过滤建模）在 P2 开工前需按 #48 先补详细设计评审并 POC——这与项目既有的"阶段启动门槛"机制正好吻合。
- **文档可信度**：技术栈 v4.1 与 PRD v2.1 的整体判断质量较高（约 30 项断言仅 1 项架构级失准、若干版本事实过时），"本地优先 + sidecar + SQLite 单事实源"的骨架经得起核查。
