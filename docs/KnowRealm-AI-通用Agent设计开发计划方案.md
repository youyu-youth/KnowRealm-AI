# KnowRealm-AI 通用 Agent 开发计划与 Grill 入口

> 状态：第一阶段（工单 01~04，可靠单步操作）已于 2026-09-22 全栈实施完结；第二阶段（三档授权、修改与批量整理，spec/tickets 见 `.scratch/general-agent-v2/`）已于 2026-09-29 实施收口（剩用户真机验收）；第三~四阶段为规划。本文是通用 Agent 后续阶段 grill 的入口文件，架构依据为[设计-4](KnowRealm-AI-通用Agent设计-4.md)，项目排期见[扩展文档 §44](knowRealm-AI-功能升级与创新扩展设计.md#446-阶段与排期2026-09-21-变更)。

按设计-4的四个阶段推进：**可靠单步操作 → 授权与批量整理 → 多资料长任务 → 条件式生态扩展。** 通用 Agent 面向当前及未来产品能力；课程和文本记录是首批验证样本，不是最终能力边界。

## Grill 使用方式与完成条件

1. 从本文开始，阅读设计-4 §5～§11、ADR-0026、扩展文档 §44 和最新 `PROJECT_PROGRESS.md`；按当前阶段核对代码，不将文档中的能力登记视为已实现。
2. 首次 grill 聚焦第一阶段：先定稿本文第二节的五项事项，再冻结第二节附带的最小能力接入、结果与版本契约。已采纳的四阶段架构和授权三档不重新作为开放选项；发现真实冲突时明确提出。
3. 每项待定事项必须形成用户确认的决定、验收条件及影响范围。10 项批量阈值、PASTE 文本语义、具体字段和预算数值仍为建议，不能仅因本文更新而视为已批准。
4. 完成条件：第一阶段无阻塞性未决项，已明确第二种真实动作复用首个动作公共机制的设计与验收方法，迁移／事务／恢复边界明确。后续阶段只记录依赖与触发条件，不提前冻结全部实现。
5. 定稿后按项目要求在同窗口完成 spec → tickets：使用 `.scratch/general-agent-v1/spec.md` 和 `issues/<NN>-<slug>.md`（创建前检查已有同主题工单并复用）。本文工单为规划单元，正式票按真实功能闭环细分，不按前后端拆分。此流程不代表已授权编写产品代码。

文档职责：设计-4管理架构原则与演进条件；扩展文档 §44管理项目定位与排期；本文管理实施次序、接入契约和验收；spec／issues管理冻结的接口、状态、字段及执行任务。发生冲突时先按设计-4和已采纳 ADR 核对并显式解决，不由计划或工单静默覆盖。

**一、计划依据与当前代码差距**

以 [通用Agent设计-4](KnowRealm-AI-通用Agent设计-4.md) 为主稿，严格保留以下架构：

> 主 Agent 理解、澄清、规划 → 统一受控执行入口 → 领域 Service → 业务数据库／JobRunner → 程序核验 → 操作回执。

不新增第二套 Agent 平台，不让 Tool 直接写业务表，不叠加运行时编排器，不创建业务事实的第二套记忆。

当前基础与实际缺口如下：

| 范围       | 已有能力                                             | 本次开发需要补齐                             |
| ---------- | ---------------------------------------------------- | -------------------------------------------- |
| Agent 骨架 | `create_deep_agent`、`AgentConfig`、声明式工具装配   | 课程查询与受控业务动作                       |
| 对话上下文 | 会话范围、历史消息、资料引用                         | 页面快照、固定目标、结构化澄清草稿           |
| 提案确认   | PENDING／APPLIED／REJECTED／FAILED、应用器、失败重试 | 操作幂等、执行结果、授权依据、批次及版本绑定 |
| 课程创建   | 领域校验、事务、搜索索引                             | HTTP 与 Tool 共用的事务内入口                |
| 文本记录   | Record、Transcript、索引、资料库回填、总结任务提交   | 提案事务接入、提交后对账、真实处理状态回执   |
| 后台任务   | JobRunner 抢占、取消、恢复钩子                       | 任务步骤、依赖等待、部分成功、跨重启接续     |
| 前端       | 聊天、流式反馈、研究入库确认卡                       | 业务确认卡、操作回执、计划卡、执行历史       |

需要特别明确四点：

- [课程创建契约 (line 59)](../backend/app/modules/course/schemas.py#L59) 不只有名称，还需要学习场景及对应的教育阶段或学习深度。
- [文本捕获 (line 36)](../backend/app/modules/capture/text_capture.py#L36) 中，带课程的 `PASTE` 会尝试提交总结；`QUICK_NOTE` 不允许指定课程。
- [提案确认 (line 94)](../backend/app/modules/library/proposals.py#L94) 自带事务，而课程 Service 也会开启事务，不能直接嵌套调用。
- [JobRunner (line 129)](../backend/app/modules/jobs/runner.py#L129) 的默认恢复包含“中断后标记失败”，不等于已经具备多步骤自动续跑能力。

已采纳的范围与排期：

1. [ADR-0026](adr/0026-agent-write-authorization-three-modes.md) 已采纳三档授权，不必重复创建 ADR。
2. 首批仅查询／读取课程、创建课程、添加课程文本记录；独立 Todo 操作不进入第一阶段。旧 G0 只表示第一阶段内的只读地基步骤，后续规格统一使用设计-4的第一至第四阶段编号。
3. 通用 Agent 波次按扩展文档 §44排在书籍拆章之前；第三阶段的多资料建课不默认具备按章拆分大 PDF 的能力。grill 核对实际依赖，不能以隐藏记录或临时解析路径替代缺失的领域能力。

**二、开工前：冻结五项实施契约**

这些属于设计-4 §11 的必要定稿，不需要重新讨论已采纳的整体架构。

| 定稿项         | 本计划建议                                                   | 必须明确的验收边界                                           |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 授权细节       | 第一阶段仅开放“请求批准”；第二阶段开放另外两档。批量自动执行阈值建议先定为 10 项 | 阈值计数、模式切换对待执行动作的影响、审计字段               |
| 文本记录语义   | 第一阶段优先复用课程 `PASTE` 处理链，并在确认卡告知会尝试生成总结 | 用户要求“只保存、不总结”时不能擅自按 PASTE 执行；若要支持，应补领域能力 |
| 业务入口与事务 | 仅抽取首批动作的事务内核心，HTTP 与提案应用器复用            | 业务写入、索引和回执原子提交；提交后任务可对账               |
| 最小持久化     | 草稿、固定目标、提案和操作结果存业务数据库；V1 不建 `agent_runs` | 重试、超时、重启后能查明是否已执行                           |
| 范围与预算     | 区分课程元信息查询、资料正文检索和写授权                     | FREE 不因页面上下文扩大资料范围；调用、重试、耗时和对象数必须有限 |

这里的 **10 项阈值、文本记录选择、具体存储字段仍是建议，不视为已经批准**。以下扩展原则随本计划确立；具体 schema、接口与兼容策略须在第一阶段 grill → spec → tickets 中冻结。

### 2.1 通用能力接入契约

| 接入项 | 最小契约 |
| --- | --- |
| 标识与参数 | 稳定动作标识、每动作类型化 schema，按领域组织；不使用无类型万能 action + payload |
| 适用条件 | 对象类型、读取范围、状态与业务前置条件；执行前重新校验目标 |
| 授权 | 后端定义操作级别与确认规则；模型不能指定授权等级、可信授权依据或执行结果 |
| 执行入口 | HTTP 与 Tool 共用领域应用服务；仅收拢本阶段接入动作的完整入口 |
| 一致性 | 明确事务所有者、操作幂等依据、对象版本检查、索引与提交后副作用及其对账 |
| 结果 | 实际状态、对象引用、关联 Job、错误和结果入口；公共字段之外保留类型化业务详情 |
| 生命周期 | 明确重试、取消、恢复与撤销的支持条件，不支持时给出可理解的原因 |

先复用现有工具与应用器注册机制，由课程创建和文本捕获验证契约；不提前引入插件平台、庞大动作基类或全部能力的实现。扩展性要求公共执行流程不增加领域专属判断，允许正常的声明式注册、schema 和展示适配。

### 2.2 公共机制与领域职责

| 归属 | 职责 |
| --- | --- |
| Agent | 理解、澄清、规划、能力装配和组织回答 |
| 公共执行机制 | 授权检查、幂等、操作状态、审计与回执 |
| 领域模块 | 业务校验、对象状态、事务写入、索引和领域副作用 |
| JobRunner | 后台领取与执行、重试及恢复机制；具体步骤与对账规则由执行体提供 |
| 前端 | 展示确认、进度与结果，提交用户授权及取消意图 |

公共机制经注册调用领域实现，不持续直接导入所有领域业务。提案框架当前位于 library 不意味着立即搬迁；仅在真实依赖需要时调整归属。公共执行层不得承载课程或记录专属规则。

### 2.3 工具装配与规模增长

- 延续 `_resolve_agent_config` 的声明式组合，按业务域组织工具，依据会话场景、允许范围及用户已启用能力装配；追加工具须保留其他 AgentConfig 字段。
- 页面上下文既不授予权限，也不把通用操作永久限制在当前页面领域；资料读取仍遵守 scope。工具暴露和执行端授权分别校验。
- 前期采用静态组合；工具增长后根据轨迹评测中的选择准确率、无效调用和上下文开销决定是否增加选择机制，不预建动态工具检索或额外意图分类模型。

### 2.4 结果展示与版本兼容

- 统一表达查询结果、待确认、执行中、部分完成、成功与失败；不能把提案 APPLIED、Job 成功与整个用户任务完成混为一谈。具体枚举及映射在规格中冻结。
- 确认卡／回执卡复用公共字段，领域提供预览与结果入口；特殊业务可提供专属组件。新增工具不默认新增一套 SSE 事件和聊天主流程分支。
- SSE 提供及时通知，持久化查询支撑断线及重启恢复；前端不直接依赖编排 Job 内部 JSON。
- 提案 payload、计划快照和操作结果需有可识别的格式版本，与防覆盖的业务对象版本分开。旧数据可兼容或迁移；无法安全解释的待执行提案须明确失效并重新确认，不能静默按新规则执行。
- 保持操作标识、状态语义和结果查询契约稳定，内部存储按设计-4的条件演进；不预建通用迁移框架。具体保留、备份和删除规则随相应持久化规格定稿。

**三、第一阶段：可靠的课程与文本记录操作**

目标是完整交付两条路径：

> “帮我创建课程” → 补齐信息 → 确认 → 创建 → 返回课程入口。
> “向指定课程添加文本记录” → 查找与消歧 → 确认 → 保存 → 返回记录及后台处理状态。

按功能闭环拆成以下工单，每张同时包含所需后端、前端和验收工作，不按技术层拆票。

| 工单                      | 工作内容                                                     | 依赖         | 完成标准                                               |
| ------------------------- | ------------------------------------------------------------ | ------------ | ------------------------------------------------------ |
| 01 页面上下文与课程查询   | 消息携带页面／选中对象快照；新增课程查找、详情读取；候选选择后固定 ID | 五项事项与最小扩展契约定稿 | 同名课程不误选，切页不换目标，FREE 不越界读资料        |
| 02 自然语言创建课程       | 随首个写动作落地最小公共执行链：澄清、schema、提案、事务、幂等、授权依据、取消检查及可恢复回执 | 01 | 未确认零创建；重复请求不重复创建；结果未知可查询 |
| 03 向课程添加文本记录     | 复用 02 公共机制及文本捕获完整链；补齐后台任务、提交后对账和处理语义展示 | 02 | 无领域专属公共流程分支；总结失败不重复建记录 |
| 04 单步可靠性综合验收 | 对 02、03 已具备的恢复、停止、错误和回执机制补充故障场景与回归 | 02、03 | 超时先查询；停止后不新增动作；失败不谎报成功 |

具体实现边界：

- 工具沿用 `propose_ingest` 的 **Pydantic 判别参数、ContextVar 绑定和既有提案应用器模式**；不是把所有动作都塞进 `propose_ingest`。
- 后端生成稳定操作标识，并通过数据库约束／条件更新防重复执行；不能只靠按钮禁用。
- 幂等依据是“同一次操作”，不能仅用课程名称或正文哈希，避免拦截用户有意重复创建。
- 澄清草稿与可执行提案分开：缺必填项的草稿不能进入确认执行。
- 沿用现有聊天工作区，增加候选卡、确认卡和回执，不新建独立 Agent 工作台。
- 断开 SSE 只代表停止接收，不能当作可靠的业务取消。执行端须在后续动作前检查取消状态；已提交的动作保留回执。

**第一阶段就要具备单步幂等和重启对账，不能推迟到第三阶段。** 第三阶段增加的是多步骤自主恢复。

**四、第二阶段：三档授权、修改与批量整理**

目标是让 Agent 能可靠处理“重命名、归类、归档、软删除、批量整理”，同时提供可审计回执和有限撤销。

| 工单                        | 工作内容                                                     | 完成标准                                                     |
| --------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 05 三档授权与操作历史       | 设置页全局默认、会话模式、执行端确定性授权规则、模式切换审计 | 默认行为不变；自动执行有完整授权依据；Memory 与审核链不受档位影响 |
| 06 单对象修改与生命周期操作 | 按动作接入修改、归档、软删除；before/after 预览、版本检查、领域副作用 | 用户修改后旧提案不能覆盖；删除后的索引、任务和掌握度处理完整 |
| 07 批量计划卡与确定性执行   | 固定对象集合、动作参数、计划版本；Run（agent_runs）＋AGENT_RUN 无状态触发 job 推进；逐项结果 | 一次批准绑定整个计划；新增对象重新确认；失败项可单独重试     |
| 08 有限 Undo 与批次验收     | 已具备可靠恢复能力的动作提供撤销；批次按依赖逆序补偿         | 撤销前检查版本及依赖；不能撤销时明确原因；取消不冒充撤销     |

必须注意：

- 工单 06 在正式拆票时按重命名、归档、软删除、跨域整理等实际闭环细分，逐票核对领域副作用与恢复条件；此处编号不是固定开发工作量。（第二阶段已按 8 张功能闭环票实施完结：执行事实地基、三档授权、修改与归档、删除与跨课迁移、批量计划卡与 Run 推进、有限 Undo 与重试、综合验收收口，另插队对象查询工具族扩展。）
- 存储已随第二阶段升级：`agent_runs` / `agent_operations` / `agent_activity` 三表落地（迁移 0030，Operation＝执行事实唯一源），授权依据、执行前快照与幂等事实由 operation 行承载。
- 跨课程整理要先检查领域是否支持。已有 API 拒绝的重新归类行为，不能由 Agent 绕开。
- 课程删除需要复用完整业务入口，包括路由当前承担的掌握度重算及重试安排。
- “完全访问”仍不能扩大已固定计划的目标集合，也不暴露物理删除、SQL、任意路径写或宿主 Shell。
- 批次执行先完成确定性任务；依赖解析结果、需要再次推理的长流程留到第三阶段。

**五、第三阶段：多资料处理与课程学习计划**

目标场景按设计-4执行：

> “把这五篇论文整理到一个新的课程中，并生成学习计划。”

| 工单                      | 工作内容                                                     | 完成标准                                                 |
| ------------------------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| 09 课程级学习计划领域能力 | 明确计划、阶段、排期、任务归属及与 Record Todo 的关系；提供真实查看／编辑入口 | 不使用隐藏 Record 承载课程计划；Agent 与界面共用领域服务 |
| 10 多资料任务执行闭环     | 固定来源、复用资料、建课、依赖等待与计划生成；同时实现步骤持久化、启动对账、推进互斥、取消和部分成功 | 不重复入库；重启只续未完成步骤；不把提交报告为可检索 |
| 11 长任务故障恢复与补偿验收 | 验证 10 的恢复机制，补齐中断、依赖失败和补偿场景；可靠性不推迟到本票才实现 | 第三篇失败不重建课程及其余四篇；补偿保留逐项结果 |
| 12 长任务端到端验收       | 故障注入、真实模型任务、Tauri 重启、部分资料继续执行         | 数据库结果、操作历史与界面展示一致                       |

存储沿用第二阶段已启用的 Run／Operation 模型：

> Run（`agent_runs`，计划版本与状态机）＋ Operation（`agent_operations`，执行事实唯一源）＋ JobRunner 内 AGENT_RUN 无状态触发 job 推进。

第三阶段在此基础上启用预留的 `WAITING_JOB` 状态（后台任务等待）并扩展多资料建课的步骤编排；若真实场景出现模型覆盖不了的等待形态，按设计-4 规定评审扩展，不把复杂状态塞进现有字段。

学习计划阶段还需保留两个边界：

- 总结及学习资产原有采纳审核不被批次授权跳过。
- 应用隐藏且 sidecar 运行时可继续；应用完全退出后保存进度，下次启动恢复，不承诺退出或关机期间继续执行。

**六、第四阶段：按条件扩展能力**

这一阶段不是前三阶段的前置依赖，也不把全部扩展强制捆绑上线。

第三阶段若多资料证据规模已顶到上下文预算，可按设计-4 §9 提前评估只读 Research SubAgent；须先满足同等委派契约与收益评测，不因阶段编号机械延后，也不作为第三阶段必备条件。

| 能力              | 启用条件                                     | 实施边界                                                     |
| ----------------- | -------------------------------------------- | ------------------------------------------------------------ |
| 内置 Skills       | 已有稳定任务流程，存在复用价值               | 先做研究整理、学习计划等少量能力包；Skill 不获得额外权限     |
| 课程长期事实      | 出现明确的目标、约束、阶段等产品需求         | 落课程／learner 业务字段，记录来源、范围、更新时间及删除机制 |
| Research SubAgent | 多资料分析需要隔离上下文，且轨迹评测证明收益 | 只读、单级委派、共享预算、取消传播、结构化结果与来源核验     |
| MCP client        | 存在真实外部集成需求                         | 保持可选，不要求普通用户额外安装运行环境；不建 MCP server    |

现有 `_resolve_agent_config()` 追加工具时仅重建 `tools` 配置；启用 Skills／SubAgent 时必须保留其余配置字段。开放委派还需检查默认子 Agent 的实际能力，不能仅解除 `task` 屏蔽。

运行时 Multi-Agent 自治协作、第二套语义记忆、通用 Undo 平台均不列入计划。

**七、开发与验收门禁**

每阶段先验收再扩大能力面；测试服务于当前改动，优先复用现有课程、文本捕获、聊天、研究、Memory 和 JobRunner 测试。

| 门禁       | 必须验证                                                     |
| ---------- | ------------------------------------------------------------ |
| 授权       | 默认档未确认零业务写入；其他档按确定性规则执行；外部内容不能授予权限 |
| 目标       | 同名消歧、切页、归档／删除后的目标失效、FREE 范围隔离        |
| 幂等       | 双击确认、并发请求、超时后查询、崩溃后重试均不产生重复业务对象 |
| 一致性     | 业务数据、索引、Job、操作回执一致；提交后副作用可恢复对账    |
| 取消与撤销 | 停止后不新增动作；已完成结果保留；撤销检查版本和依赖         |
| 长任务     | 部分成功、依赖失败、重启续跑、计划变更重新授权               |
| 产品回归   | 普通问答、研究提案、RAG 引用、Learner Memory、总结审核保持原有约束 |
| 扩展性 | 用文本捕获及后续真实能力验证授权、幂等、确认和回执复用；公共执行流程无领域专属分支，不为验收创建虚假插件 |
| 兼容性 | 历史提案与结果可安全读取；不兼容提案明确失效并重新确认；SSE 重连／重启后查询状态一致 |

实施时的常规验证：

- 后端相关 pytest、Ruff、Pyright；测试使用独立临时目录并清理。
- 前端相关 Vitest、lint、build；新增文案同步 `zh.json` 与 `en.json`。
- 后端契约变化后重新生成并检查 API 类型。
- UI 实施遵循 DESIGN.md 与 impeccable，复用现有组件。
- 阶段收口安排真实 Tauri／WebView2、真实模型和重启验收，自动化测试不代替真机证据。
- 权威文档增补先提案；实施完成后同步进度，`PROJECT_PROGRESS.md` 保持 200 行以内。

推荐实施顺序为：

**五项事项及最小扩展契约定稿 → 01～04 单步闭环 → 05～08 授权与批量 → 09～12 长任务与课程计划 → 条件式生态扩展。**

这份计划中，第一阶段可以立即进入规格细化；后续阶段已明确交付目标与依赖，具体表结构、预算数值和撤销规则按设计-4要求在对应阶段前定稿，避免提前冻结尚未验证的设计。
