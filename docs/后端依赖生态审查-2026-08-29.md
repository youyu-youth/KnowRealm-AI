# 后端依赖生态审查（2026-08-29）

> **文档定位**：对《技术栈设计与审查 v4.4》后端部分的**生态实测佐证与增补建议**——用 2026-08 的 PyPI/GitHub 实测数据复核既有自研决策，并登记本次审查后新增/待触发的候选依赖。选型权威仍以 v4.5 为准，本文不另立结论。
> **审查范围**：`backend/app` 全部约 1.4 万行 Python 源码；对照生态 = 调研当日 PyPI 最新发版、官方文档、维护状态（含社区 fork 信号）。
> **总审查结论**：**无高优先级替换项**。主流框架选型全部正确；自研部分是"零部署、单进程 sidecar"约束下的合理自研，通用框架无法满足约束或引入净风险。本次审查唯一落地的替换为 DataDirectoryLock → filelock（见 §三）。

## 二、自研实现逐项裁决

### 2.1 JobRunner 任务队列（`app/services/job_runner.py`）——保留（佐证 v4.4"自研 processing_jobs 队列"决策）

生态实测（2026-08）：Celery / RQ / arq / Dramatiq / Taskiq **全部需要外部 broker**（Redis/RabbitMQ），直接违反零部署约束；Huey 有 SqliteHuey 后端但是线程 worker + 独立 consumer 进程模型，且有已知的 SQLite 写争用 database-locked 问题；Procrastinate 为 PostgreSQL-only。

更本质：该队列深度绑定业务状态机——三态领取协议（Ready/Cancel/Waiting）、条件 UPDATE 抢占（rowcount==1）、三种失败记账（终态/固定重试/指数退避）、CANCELLED 静默契约、SSE invalidation 协议点。通用队列无法表达这些语义，套用等于在其上再写一层状态机，复杂度净增。**结论：合理自研，不换。**

### 2.2 腾讯 ASR 客户端（`app/services/tencent_asr_client.py`，手写 TC3 签名）——保留

官方 SDK（`tencentcloud-sdk-python-asr` 3.1.166，实测 PyPI：wheel 46.8 KB，2026-08-27 仍在发版，async 客户端已用 httpx）体积小且活跃，但四个净风险使其不适配本项目：

1. **pyright strict 硬伤**：官方 SDK 无类型标注（无 py.typed），strict 门禁下每个调用点需 ignore；
2. **重试语义冲突**：新版 SDK 自带 retry/熔断拦截器，与本项目 `max_retries=0`、重试归 job 状态机的哲学冲突——SDK 自动重试会污染 attempts 失败记账；
3. **测试 seam 弱**：SDK 的 http client 为内部自建属性、非构造注入，现有 `FixtureTencentAsrTransport`（httpx transport 注入）体系需重写；
4. 201 行中约一半是防御性响应解析，换 SDK 后照写不误。

**触发重评条件**：接入腾讯云第三个及以上服务时，SDK 收益转正。

### 2.3 迁移系统（`app/db/migrations.py`，user_version + 编号 SQL）——保留，条件触发再议（佐证 v4.4 既定决策）

Alembic 1.19.1（2026-08 仍活跃；async 模板 + aiosqlite + batch 模式均官方支持）能带来 autogenerate diff、downgrade、分支合并，但代价是 env.py 样板 + "迁移即纯 SQL 文件"心智模型被打破 + sidecar 需编程式调用。单人项目 + 只向前迁移 + 单部署单元用不上其核心收益；现有 6 处测试 `user_version` 断言的手动同步是测试组织问题，Alembic 不解决。**触发重评条件**：多人协作、迁移数量翻倍、或出现 schema drift 疑虑。

### 2.4 其余自研点——均保留

| 自研点 | 保留理由（一句话） |
|---|---|
| `local_config.py` JSON 配置读写 | 运行时 UI 可写的用户文档存储，非 env 配置；"写默认值=删键/未知键透传"是业务决策 |
| `llm_call_logs` 自研埋点 | Langfuse 要 Docker、OTel 要 collector，违反零部署；DB 表只记元数据正合适 |
| ffmpeg 两段 subprocess | `create_subprocess_exec` 标准做法；ffmpeg-python 只是参数 builder 且长期低维护 |
| `RecordInvalidationNotifier`（22 行） | SSE 失效通知挂载点，无可替代需求 |
| `ISODateTime` 自定义类型（8 行） | SQLAlchemy 标准扩展点，解决 SQLite 微秒精度 |

另记一处**内部重复**（非轮子问题）：`agents/llm.py` 四个 `call_xxx_model` 仅差 graph_name/error_code 等三个常量，可收敛为带参函数，留待顺手重构。

## 三、已执行：DataDirectoryLock → filelock（commit 4025f43）

- **动机**：消灭 60 行 msvcrt/fcntl 平台分支 + 锁边界交社区实现兜底；无已知 bug。
- **对外契约全保真**：`DataDirectoryLock` 类名、`acquire/release` 接口、`DataDirectoryInUseError`、消息文本 `DATA_DIRECTORY_IN_USE：数据目录正在使用`、`.knowrealm.lock` 文件名均未变；`Timeout` 内部转译。
- **验收**：274 测试全绿（含双开端到端与杀进程重启）、ruff 全过、pyright 无新增。
- **实测经验（换库时踩点记录，后续依赖审查可复用）**：
  1. **`timeout=-1`（filelock 构造器默认值）= 无限阻塞等待**，不是"立即失败"——立即失败须用 `timeout=0` 或 `acquire(blocking=False)`。若用错，双开的第二个 sidecar 会静默挂在 lifespan；
  2. **filelock 的锁随对象 GC 自动释放**（`AcquireReturnProxy` 的由来）——持锁期间必须持有 `FileLock` 实例引用；
  3. `preserve_lock_file=True` 用于保持锁文件残留的磁盘形态与旧实现一致（filelock 默认 release 时删除锁文件）；
  4. Windows 后端 3.32.x 为 ctypes 直调 `NtCreateFile` + `LockFileEx`（带 reparse 防御），实测跨进程互斥正确——**双进程对照实验是验证锁语义的必要手段**，同进程双实例会被 filelock 的死锁检测拦截、测不出真实争锁行为。
