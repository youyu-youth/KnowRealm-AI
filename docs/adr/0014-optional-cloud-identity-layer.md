# 账号体系定位为可选云身份层，桌面端永不强制登录

---
Status: accepted（2026-08-30，用户模块登录功能 grilling 定稿）
---

用户模块讨论提出引入"真实登录"（邮箱+密码+GitHub OAuth，参照 ChatGPT/Warp/opencode）。调研证实：三者登录的对象都是**厂商运营的云服务**，本地核心全部匿名可用——Warp 2024-11 撤销强制登录（与开源客户端同期），opencode Zen 官方标注 "completely optional"。本地优先架构（ADR-0001）下桌面应用自身没有验证对端：sidecar 只绑 127.0.0.1、事实源在用户磁盘，应用内自存密码哈希可被任何拿到数据目录的人绕过（安全剧场）。同时"多人数据隔离"与"会员/账号"是正交问题：前者由 OS 账户天然覆盖（`desktop.json` 存 `app_config_dir()`、默认数据目录 `%USERPROFILE%\KnowRealm\`，均按 OS 用户分置——数据、偏好、供应商 key 全隔离，零开发），后者才需要云端身份。

**决定**：

- 桌面端**永不强制登录**；"账号"重新定义为**未来可选云身份层**（Raycast/Obsidian/Zen 模型）——登录仅用于授权云服务与会员权益，数据永不出本地，#55 存储范式不变；
- 会员=云服务订阅，本地功能永不设墙（开源仓库内本地付费墙 fork 即拆）；
- 偏好形态=邮箱+密码+GitHub OAuth；**触发时按成本梯度复核**（托管 Auth/纯 OAuth 优先，不自建密码体系）；
- 触发条件=**决定运营 KnowRealm 云服务/启动商业化那天**；落地页与账号门户属未来云服务项目，不在本仓库；
- 桌面端**不预埋任何代码钩子**：ADR-0013"一安装一数据目录"已天然支持未来"一云账号 ↔ 一本地数据目录"映射。

## Considered Options

| 方案 | 结论 |
|------|------|
| **A. 可选云身份层（本地匿名可用，登录仅 gate 云服务）** | **采纳**——参照系共同形态；同时保住零部署开源卖点与未来商业化空间 |
| B. 桌面端强制应用级登录 | 否决——参照系无一支持（Warp 已回退）；本地优先下无验证对端 |
| C. 云端事实源+全量同步（ChatGPT 模型） | 否决——#55 整体重开，放弃零部署定位 |
| D. 现在自建完整账号体系（邮箱+密码全套） | 否决——无云服务存在即无登录对端；邮箱体系是永续运营负担而非一次性开发 |
| E. 应用内本地账号（本地口令/多账户） | 否决——无验证对端即安全剧场；OS 账户已提供隔离 |

## Consequences

- 基线升版 v2.4：Q15 登录侧定稿（分享形态仍搁置）、#3/§7 认证行/§5.2 排除清单连锁改写；GLOSSARY.md 增「账号（Account）」词条并与「档案（Profile）」解耦。
- 若未来出现"多人共用同一 OS 账户"场景（机房/家庭），"应用内档案切换器"作为独立本地工单立项，与账号体系无关。
- 触发日启动时：云服务选型（托管 Auth vs 自建）与桌面端接入方式（系统浏览器 OAuth 回跳 + token 加密存储）另行 grilling 定稿。
