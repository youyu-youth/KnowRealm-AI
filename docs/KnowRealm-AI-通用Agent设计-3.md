# KnowRealm 通用 Agent 设计分析

## 一、总体结论

**这个愿景在现有架构上不需要新框架，需要的是三个增量：操作域工具层、页面上下文通道、计划执行层。** 但它与三处既有定案存在直接张力（§41.1「不上通用自主 Agent」、免确认写路径 vs 硬门禁、Multi-Agent 否决），属于**产品方向级变更，须显式翻案并走 grill→spec，不能默默实施**。

关键认知：你们其实已经走在这条路上四步了——`search_library`（读）、`web_search`（外部读）、`propose_memory` / `propose_ingest`（受控写提案）。「通用 Agent」不是范式转变，而是把「提案-确认-执行」模式从研究/记忆两个特例**推广为操作域的通用模式**。

## 二、愿景六能力 × 现状地基对照

| 用户要的能力      | 现状                                                         | 缺口                                                         |
| ----------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 意图理解          | deepagents 工具循环天然承担（模型按工具描述自选，无需意图分类器） | **没有操作域工具可选**——模型想建课程也无从操作，这是第一缺口 |
| Tool Calling      | 4 个自研工具 + ContextVar 运行期绑定 + `ToolCallBudget` 预算纪律 | 只有内容检索与 2 个特化写提案；缺导航类只读工具（“查我的课程列表”都不行）与操作类提案工具族 |
| Clarification     | 模型多轮对话天然支持；Learner Memory V1（§43）已提供跨会话用户事实注入 | 缺**页面环境快照**：当前路由/课程/选中对象未进上下文，"帮我加一条记录"无法锚定当前课程 |
| Context Awareness | 五档 scope = 授权边界（会话内不可变）+ 挂载失效派生（record_deleted 等） | scope 只约束检索授权，不承载“用户现在在哪”的提示性环境（两者是正交的，后者缺） |
| Planning          | 单轮内多步规划 = 工具循环已支持                              | 跨确认/跨后台的计划型任务缺执行层（但样板已存在，见下）      |
| Task Execution    | Course Brain 构建 job = “多来源收集→分块→LLM 抽取→确定性归一→发布” + 前端六态轮询，**这就是计划型长任务的完整样板**；JobRunner 崩溃恢复在产 | 未通用化；SSE `tool_call/tool_result` 过程反馈已有但只覆盖单轮 |

## 三、核心设计：三个增量，一台面上的纪律

### 增量 1：操作域工具层（最大缺口）

原则沿用 §42.15 职责定案，工具分三类：

```text
读工具（免确认，直接返回）
  course__find / record__find / todo__find …   ← 导航查询，走业务 Service 只读接口
  search_library（已有，内容检索，与导航查询职责不同）

写提案工具（只提案，永不直接写业务表）
  propose_course_create / propose_record_create / propose_todo_create
  propose_organize（归类/移动/归档建议）
  ← 全部照 propose_ingest 模式：@tool + Pydantic 判别 schema + ContextVar 绑定
    + 条数上限超限拒绝 + 落 agent_proposals(PENDING)

计划提案工具（G2 阶段）
  propose_plan：复杂任务先出计划清单（步骤、涉及对象、需确认点），整计划一个确认卡
```

不做万能 `propose_action(action_type, payload_any)`——payload 无法判别校验，`agent_proposals` 的 `_PAYLOAD_SCchemas` 判别体系（`proposals.py` 已有）就废了。按域一族工具、每族一个判别 payload。

**不做前置意图分类器**：七个意图分类（查询/创建/修改…）与工具族不是一一映射（“整理” = find + propose_organize 组合），工具循环本身就是路由；前置分类器是第二次 LLM 判断，违反「脚本优先、LLM 次之」。意图纪律进 system prompt（“创建类请求先核对必要参数，缺则一次问齐”）而非架构组件。

### 增量 2：页面上下文通道

- 前端发消息请求体附带**环境快照**：当前路由、当前课程/记录/资料 id、当前选中对象摘要（复用已有 `last_route` 导航记忆的采集点）。
- 后端注入 system 末尾（与 learner 块、联网指引同位、同预算），**提示性而非授权性**——授权仍由 scope 唯一决定，提示只影响模型默认理解（“当前处于课程 X"）。
- 与 scope 的关系定案：scope 是不可变授权边界（现状），环境快照是每轮可变的提示上下文。用户例子“在当前课程加记录" = COURSE scope 会话（或 FREE+环境快照）。

### 增量 3：计划执行层

- **短任务**（一轮工具循环 + 一次确认可完成）：零新增，天然支持。
- **长任务**（“5 篇论文→建课→生成学习计划”）：**不让 chat graph 长跑**（§42.4 定案"Graph 无需跨小时/跨天暂停"仍正确）。形态 = `propose_plan` 出计划 → 用户确认计划 → **落一个编排型 job**（确定性步骤直接执行、LLM 子步骤如“生成学习计划”走既有 LangGraph 域）→ 前端复用 CB 六态轮询。样板 = `CONCEPT_EXTRACTION` 构建 job。
- **不建通用编排引擎**：按场景建 job 类型（与 §41.3“不做对象驱动模板”同理），首个真实场景就是“批量入库 + 建课 + 生成任务”，它天然是书籍拆章波次的邻居。
- 中断/继续/重规划就此解决：未确认的计划 = 自然中断点；执行中 = JobRunner 恢复纪律；重规划 = 改计划重新确认。**不需要** LangGraph interrupt 跨天挂起。

### 不可动摇的既有纪律（写路径）

`Agent → 提案 → agent_proposals → HITL 确认 → 领域 Service 执行`（§42.6 V1.1 已定稿）。这同时就是你要的“高风险操作确认机制”的地基，往上加**分级确认**（确认级别由确定性规则映射，不耗 LLM）：

| 级别 | 操作                 | 确认形态                                                     |
| ---- | -------------------- | ------------------------------------------------------------ |
| L0   | 读/检索              | 免确认（现状）                                               |
| L1   | 单条创建             | 提案卡一键确认（展示完整参数，信息齐全时一张卡一个按钮——摩擦已最低） |
| L2   | 修改/移动/归档       | 确认 + before/after 预览                                     |
| L3   | 删除/批量/跨课程移动 | 逐项确认 + 明示可撤销性                                      |

## 四、其余机制逐项裁定

- **执行状态与反馈**：SSE `tool_call/tool_result` 已覆盖单轮；确认卡已有（研究入库/记忆提案两处先例）；计划执行进度复用 CB BUILDING 轮询模式。零新机制。
- **失败重试与恢复**：三层已有——工具失败走 `ok=false` 载荷不炸流（web_search 先例，模型自行说明）；提案天然可重放（PENDING 不改事实）；job 走 JobRunner 恢复。批量语义 = 提案逐条独立，部分成功天然支持。缺口仅是批量卡上“3 成功 2 失败”的呈现。
- **Undo 与操作历史**：事实层软删 + 30 天回收站已有（Record/Course/LibraryItem）；操作层 `agent_proposals` **本身就是操作历史事实源**，补执行结果回写（applied_at / result / batch_id 分组）+ 会话“AI 操作"时间线视图即可。**不做通用 Undo 框架**——各域恢复语义不同（§42.10 明确 Record/学习资产删除规则不扩张），逐域复用各自生命周期动作。
- **用户 Memory / 项目 Memory**：用户 Memory = Learner Memory V1（已定稿，勿动）；**项目 Memory 不建**——项目状态就是业务表本身，Agent 经工具实时读取才是事实源，复制进记忆层必然漂移（红线 #2 精神）。
- **RAG/Memory/Skills/MCP/Tools“统一编排”**：警惕“编排器”这个词。你们已有的 `_resolve_agent_config` 按 mode × scope × 开关**声明式组合**工具集——这就是统一编排的正确形态（装配期组合，非运行时引擎）。各能力经既有接口接入：RAG = `LibraryRetrievalService` 单深模块、Memory = learner 注入块、Skills = 场景包（prompt 资产化，§39.3 已定）。不要在它们上面再叠一层 orchestrator。
- **MCP**：触发条件“自研工具 ≥3 且轨迹评测通过”——工具数已到 4，研究黄金集已落位，操作工具族上线后自然到达评估点。届时评估的是 **MCP client**（用户接外部工具服务器，仍受红线 #11 仅聊天域）；MCP server 维持不做（单机个人数据定位）。
- **SubAgent**：维持 §42.14 条件门（“独立上下文窗口/并行收益经评测成立”）。批量论文解析这类场景由 JobRunner 并行 job 承担，不需要 agent 间通信；红线 #2 禁 Multi-Agent 运行时通信的裁定**当前没有必须翻案的场景**。

## 五、与既有定案的冲突点（须你拍板，不能默默实施）

1. **§41.1 第 5 条明文「不上通用自主 Agent」**——本提案实质是修订该口径。这是产品方向变更：应新开扩展文档章节（如 §44）并回写 §41.1，走 grill→spec→tickets 同窗口流程。
2. **"信息足够则直接创建（免确认）" vs §42.11 硬门禁「未经确认写入事实 = 零」**——我建议**维持确认门、把摩擦降到 L1 一键**，理由：本地单用户的数据是核心资产，“用户可见可治理”是本地优先的立身之本；静默写入一旦错建（课程名错/重复建）会侵蚀信任。若你要真正的免确认档，需显式翻案硬门禁并定义豁免面（如仅 Todo 创建），我不推荐。
3. **排期**：当前队列为研究会话真机验收 → 书籍拆章。通用 Agent 是大波次，建议排书籍拆章之后（“批量入库建课”计划场景与拆章基建咬合）；若要插队须显式变更 §41.1 排序。
4. Multi-Agent / 通用 Skills 框架 / MCP server 三个“明确不做”：你的提案触到边界的只有 MCP（client 方向可评估）与 SubAgent（条件门维持），**建议不翻案**。

## 六、分阶段路线建议

- **G0 地基（小）**：页面环境快照通道（请求体字段 + system 注入 + 预算）＋导航类只读工具（`course__find` 等，走 Service 只读接口）＋操作指令 prompt 纪律 + prompt_version bump。
- **G1 写侧最小闭环**：提案工具族首批（课程/记录/Todo 创建）＋确认卡复用（研究会话卡模式）＋分级确认规则器（确定性映射）＋`agent_proposals` 扩展（新 proposal_type 判别 payload、执行结果回写、batch_id）。验收 = 你的两个例子：「创建课程」多轮澄清一次问齐→卡→建；「课程内加记录」scope+环境快照锚定。
- **G2 计划与批量**：`propose_plan` ＋首个编排型 job（批量入库建课生成任务）＋六态进度反馈＋修改/移动/归档/整理域（L2 确认 + diff 预览）。
- **G3 生态**：MCP client 评估（届时触发条件满足）、工具轨迹评测扩到操作域（黄金集：澄清轮次、参数正确率、越权尝试拒绝——复用 `docs/evaluation/` 模式）、SubAgent 条件门复核。
- **明确不做**：前置意图分类器、通用编排/Undo 框架、第二套记忆、运行时 Multi-Agent、MCP server、免确认写路径。

数据模型影响很小：`agent_proposals` 扩枚举与回写列 + 聊天请求体环境快照，基本零新表——符合“产品层可激进、模型层保持克制”的定位。事务纪律沿用 B6 定案（路由编排层统一事务）。
