# 补充推荐：项目尚未引入、未来可能用得上的库

## A. 近期即可落地（工程化，零风险）

### 1. `openapi-typescript`（前端侧，npm）——前后端类型对齐自动化 ⭐ 最踏实的一项

后端 `app/main.py:231` 已经暴露了 `/api/openapi.json`，而前端的请求/响应类型目前是手写维护的。用 [openapi-typescript](https://github.com/openapi-ts/openapi-typescript)（openapi-ts 组织，drizzle 团队成员主导，周下载百万级）从这个 JSON 自动生成 TS 类型，前端 `apps/desktop` 的 API 层就能与 Pydantic schema 保持编译期同步。**不引入任何运行时依赖，纯构建期工具**，符合“SQLite 唯一事实源 + 类型安全”的项目哲学。引入成本：一条 npm script + 把手写类型迁移到生成类型。同类对比：`orval` 更重（连 react-query hooks 一起生成），项目已有自己的 query 封装，`openapi-typescript` 只生成类型更贴合现状。

### 2. `pytest-cov` + `pytest-timeout`（测试基建）

- `pytest-cov`：上轮已提，覆盖率基线量化 1.4 万行的测试盲区；
- `pytest-timeout`：记忆里有“TodoPanel 全量跑间歇超时=既有抖动”的经验，后端测试同样存在长挂风险（JobRunner 轮询测试、SSE 流测试都是真实的等待循环）。`pytest-timeout` 能把“卡死”从“CI 超时”变成“精确到测试用例的诊断”，两者都是纯 dev 依赖。

## B. 路线图直接对应——chat 检索工单（`chat.py:216` 已预告"检索工具为后续工单”）

这是最值得提前做技术储备的方向，按“零部署合规度”排序：

### 3. SQLite FTS5 + trigram tokenizer（零新依赖，首选起点）✅

SQLite 3.34+ **内置** trigram tokenizer，对中文做子串级全文检索可直接使用（`CREATE VIRTUAL TABLE ... USING fts5(text, tokenize='trigram')`）。数据仍在一个 `knowrealm.db` 里，完全符合 #55/#56"SQLite 唯一事实源”决策和“模型层保持克制（零新表模式）”。**建议作为检索工单的第一步：先子串检索，质量不够再升级向量**。注意 aiosqlite 随 Python 3.12 自带的 SQLite 版本 ≥ 3.34，无兼容问题。

### 4. `sqlite-vec`（向量检索，语义搜索升级路径）

[sqlite-vec](https://github.com/asg017/sqlite-vec) 0.1.9（2026-03-31 发版，纯 C 无依赖，作者 Alex Garcia——SQLite 生态核心贡献者）。核验到的真实状态要如实告知：**pre-v1、作者周末业余维护**，2025 年曾因更新缓慢出现[社区关切](https://github.com/asg017/sqlite-vec/issues/226)和[社区 fork](https://github.com/vlasky/sqlite-vec)，但 2026 年已恢复活跃（v0.1.9 修复了 DELETE 内存泄漏，DiskANN 索引在路上）。

为什么仍推荐：向量数据以 `vec0` 虚拟表形式存在**同一个 SQLite 文件里**，是唯一不破坏“单一数据目录可搬移”承诺的向量方案。对比项 LanceDB（嵌入式、活跃、Rust）虽也免部署，但引入独立文件格式 = 第二存储引擎，破坏唯一事实源。**建议**：等检索工单立项时再引入，锁定版本、embedding 由现有 LLM 供应商 API 提供（不本地跑模型），表结构与现有迁移体系（`migrations/NNNN_xxx.sql`）衔接。

### 5. `jieba`（中文分词，条件触发）

若 trigram 的子串匹配精度不满足（如“机器学习”搜不到只含“机器”的段落这类分词需求），FTS5 预分词方案需要 jieba。**但它是维护近乎停滞的经典库**（功能稳定、无安全风险），且分词入库会让 FTS 表与原文产生同步复杂度——所以我把它列为“trigram 实测不够后再考虑”的备选，不是默认推荐。

## C. 产品方向候选——学习场景深化

### 6. `fsrs`（py-fsrs）——间隔重复调度算法 ⭐ 与产品定位最契合

[py-fsrs](https://github.com/open-spaced-repetition/py-fsrs) v6.3.2（2026-08-09 发版，open-spaced-repetition 官方，与 Anki 23.10+ 内置调度器同源同维护生态）。核验过依赖：**运行时仅依赖 `typing-extensions`**（torch/numpy 只在可选的 optimizer extra 里），零部署完美合规。

为什么值得：KnowRealm 已有知识点表（knowledge_points）、习题（quiz）、复习场景是学习助手最自然的演进方向。FSRS 是当前间隔重复领域的事实标准算法（[生态全景](https://open-spaced-repetition.github.io/awesome-fsrs/)），自研调度算法是真正的“重复造轮子”——这里的轮子又新又好。引入形态：纯函数库，复习记录落 SQLite（新增一张复习历史表 + 每个知识点的记忆状态字段），与现有 JobRunner/迁移体系无冲突。**触发时机：立项“知识点复习/记忆巩固”类工单时**。

### 7. `rapidfuzz`——文本去重与模糊匹配

rapidfuzz 3.14.5（2026-04 发版，C++ 实现，活跃）。用途：quiz 生成去重、知识点相似合并建议、capture 归类辅助。纯本地计算、无网络无依赖。触发时机：当 LLM 生成的习题/知识点重复问题实际出现时再引入，不必预装。

## E. 远期谨慎项（不主动推荐，仅记录）

- **本地转写**（faster-whisper / pywhispercpp）：零云端依赖的终极形态，但模型下载（数百 MB 起）、CPU 推理延迟、打包体积都与“模型层保持克制”冲突。触发条件只有一个：隐私需求强到用户愿意接受体积与速度代价。
- **APScheduler**：定时调度。现有 JobRunner 的 DB 轮询模式已覆盖“到期任务”语义（`next_run_at`），再引入是重复建设，**明确不推荐**。
